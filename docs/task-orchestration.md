# 업무 경계와 복합 요청 오케스트레이션

사용자 요청 → `work` 스킬의 결과·동작 분류와 검토 판단 → 구조화 계획 → 실행 서비스의 DAG 검사·예약 → 작업별 검증과 선택된 검토·수정 → 완료 산출물 전달로 이어진다. 스킬은 원래 요청을 해석하고 실행 서비스는 실행 순서와 상태를 소유한다. GUI는 카탈로그 설정과 실행 결과를 관리한다.

## 기본 진입 기준

`work`는 구체적인 결과의 작성·수정·계획·분석·조사·검증·구현·검토를 맡기는 프롬프트의 기본 진입 스킬이다. 사용자가 WorkLog나 스킬 이름을 붙일 필요는 없다. 일상 대화, 별도 업무 실행이 필요 없는 단순 설명, 스킬·하네스를 사용하지 말라는 명시적 요청은 제외한다. “PRD가 뭐야?”는 직접 설명할 수 있지만 “이 요구사항으로 PRD를 작성해 줘”는 등록 업무로 분할·실행한다.

이 동작은 스킬 설명과 지시문의 기본 선택 기준이다. 플랫폼이 스킬을 발견·선택하는 방식에 의존하므로 description이나 심링크 설치만으로 모든 프롬프트의 자동 진입을 100% 강제한다고 보장하지 않는다. 기록 훅은 스킬의 선택·실행과 별도로 입출력을 수집한다. 기본 진입은 기존 작업 권한이나 유료 호출·외부 변경에 대한 승인을 확대하지 않는다.

## 작업 경계

[전체 카탈로그](job-catalog.md)의 63개 사용자 업무와 5개 시스템 업무는 각자 `boundary.owns`, `excludes`, `inputs`, `deliverable`, `acceptance`를 가진다. 서비스 시작 시 누락된 경계·규칙·스키마·실행 프로필을 거부한다. 이 경계와 `JOB-BOUNDARY-001`은 생성·검토·수정 프롬프트에 포함되고 로컬 지시문 설정과 별도로 고정된다. 독립 검토가 필수인 작업은 경계 준수 근거를 생략하면 완료할 수 없다.

이름이 비슷한 업무는 수행 동작과 최종 결과로 구분한다. `bug.analyze`는 원인 보고, `bug.fix`는 요청한 결함의 소스 변경, `refactor`는 동작 보존 변경이다. `test.scenarios.plan`은 검증 절차, FE·BE 테스트 업무는 테스트 코드, `checks.run`은 등록 명령의 실제 실행이다. 새 문서 작성·기존 문서 수정·문서 검토를 서로 대체하지 않는다.

스킬은 먼저 카탈로그를 확인하고 제공 자료의 이름과 요청한 결과를 구분한다. “기존 PRD를 참고해 화면 명세와 목업 작성”에는 PRD 생성 작업이 없다. PRD 안의 수용 기준이나 업무 자체의 검증·수정 단계도 별도 사용자 산출물로 중복 분할하지 않는다. 스킬을 거치지 않는 `run`의 자연어 분류는 제한된 호환 기능이며 모호한 요청을 임의의 업무로 실행하지 않는다.

“기존 PRD와 API 설계로 팀에 공유할 문서를 작성”은 `document.share.create` 한 작업으로 분류한다. `source_text`에 원문 또는 제공 자료 중 사용할 범위를, `audience`에 독자를, `purpose`에 공유 목적을 넣고 필요한 `constraints`만 추가한다. 사전 맥락이 없는 독자가 배경·목적부터 핵심 내용, 확인된 결과·영향, 요청·다음 행동까지 이해하는 문서를 만든다. PRD·API 신규 산출물을 따로 요청하지 않았으면 재생성하지 않는다. 신규 PRD와 이를 바탕으로 한 공유 문서를 함께 요청한 경우에만 두 결과를 분할하고 의존성을 연결한다.

`input_files`로 첨부한 본문은 `source_text`에 중복해서 붙여 넣지 않아도 된다. 선행 산출물을 사용할 때는 `source_text`에 “제공된 선행 결정 기록 파일만 기준으로 사용한다”처럼 자료 범위만 명시하고 `depends_on`으로 전달되는 검증된 스냅샷을 읽으며, 아직 생성되지 않은 본문이나 미래 파일 경로를 추측하지 않는다.

목표 대비 현황 보고는 `status.report`, 다른 사람이 이어서 수행할 인수인계는 `handoff.create`, 전용 유형이 없는 문서는 `document.create`가 담당한다. 캘린더의 내부 `work.report.create`는 선택 기간의 로컬 이력을 정리하며 공유 문서 작업을 대신하지 않는다. 기존 공유 문서의 검토·수정만 요청했다면 `document.review`·`document.update`로 분류한다. 공유용 문서 작성이 실제 전송·게시를 포함하지는 않는다.

“테스트 시나리오 검토”, “검증 보고서 검토”, “테스트 실행 결과 검토”는 기존 자료의 `document.review`다. 이를 시나리오 생성·보고서 생성·검사 실행으로 바꾸지 않는다. 동작이 없는 “검증 보고서”나 “E2E 실행 후 검토”처럼 복합 작업이 필요한 요청은 단일 `run`에서 임의 실행하지 않고 `work`의 구조화 계획 또는 지원되는 로컬 검사 호출로 안내한다.

## 작업별 검토 판단

카탈로그의 `review_policy`는 `default_required`, `omission_allowed`, `scope`를 제공한다. 스킬은 각 계획 step에 `review: {"required": boolean, "reason": "판단 근거"}`를 넣는다. 직접 `run` 요청도 같은 필드를 사용할 수 있다. `reason`은 1~1,000자의 비공백 문자열이며 해당 결과와 근거 자료에 맞춘 이유다. 생략한 기존 요청은 등록된 workflow를 유지한다.

| 결과와 요청 | 선택 |
|---|---|
| 사용자가 명시적으로 요청한 검토 | `required: true` |
| 요구사항·설계·코드처럼 후속 결정과 동작에 영향을 주는 산출물 | `required: true` |
| 조사·원인 분석·비교처럼 사실 주장과 근거 판단이 필요한 결과 | `required: true` |
| 제공된 사실을 짧은 문구나 정해진 형식으로 바꾸는 단순 텍스트 | `omission_allowed: true`이고 새로운 판단·사실을 추가하지 않을 때만 `required: false` |

현재 사용자 업무 중 생략을 허용하는 유형은 `text.generate`뿐이다. PRD·설계·코드·조사·검토 업무에 `false`를 보내면 실행기가 거부한다. 스킬은 검토를 생략하려고 전용 업무를 텍스트 업무로 바꾸지 않으며 짧은 요청·적은 파일 수·시간 압박만으로 생략하지 않는다. 혼합 요청은 결과별로 판단하고, 생략 근거가 불명확하면 검토를 유지한다. 생략 가능한 업무인지의 상한은 코드가 검사하지만 자연어 `reason`의 의미까지 자동으로 증명하는 것은 아니다.

사용자가 검토를 명시적으로 제외했는데 해당 업무의 필수 게이트와 충돌하면, 그 조건으로는 하네스 실행을 지원할 수 없다고 설명한다. 제외한 검토를 몰래 추가하거나 작업 유형을 바꿔 필수 게이트를 우회하지 않는다.

`false`는 별도 모델 검토의 생략이다. 입력·응답 스키마, 변경 범위, 입력/산출물 해시, 지원되는 실행 검사와 출력 계약은 유지한다. 검토만 요청한 업무의 대상 검토 자체를 생략하거나 그 대상을 수정할 권한을 주지 않는다. 검토 보고서 완료와 검토 대상의 합격도 구분한다. 시스템 `session.summarize`·`text.rewrite`는 고정된 단일 생성 workflow를 사용하며 이 사용자 업무 선택 필드의 대상이 아니다.

## 계획 계약

`POST /plans` 또는 `harness orchestrate --input plan.json --wait`가 `contracts/plan-request.schema.json`을 사용한다. 일반 사용자는 프롬프트를 주고 스킬이 내부 계약을 만든다.

```json
{
  "prompt": "초대 기능의 PRD를 작성하고 그 결과로 화면 명세와 엔티티를 설계해 주세요.",
  "idempotency_key": "one-original-invocation",
  "steps": [
    {
      "id": "prd", "task": "prd.create", "output_key": "invitation-prd",
      "request_excerpt": "초대 기능의 PRD를 작성",
      "input": { "requirements": "초대 기능의 요구사항과 관찰 가능한 수용 기준을 작성한다." },
      "review": { "required": true, "reason": "제품 요구와 수용 기준이 후속 설계의 기준이 됩니다." },
      "depends_on": []
    },
    {
      "id": "screen", "task": "screen.specify", "output_key": "invitation-screens",
      "request_excerpt": "그 결과로 화면 명세와 엔티티를 설계해 주세요.",
      "input": { "requirements": "선행 PRD의 화면 상태·권한·예외 동작을 명세한다." },
      "review": { "required": true, "reason": "권한과 예외 화면이 제품 요구에 부합하는지 판단해야 합니다." },
      "depends_on": ["prd"]
    },
    {
      "id": "model", "task": "entity.design", "output_key": "invitation-entities",
      "request_excerpt": "그 결과로 화면 명세와 엔티티를 설계해 주세요.",
      "input": { "requirements": "선행 PRD의 엔티티·관계·불변식을 논리 모델로 설계한다." },
      "review": { "required": true, "reason": "관계와 불변식은 구현에 영향을 주는 설계 결정입니다." },
      "depends_on": ["prd"]
    }
  ]
}
```

각 계획은 최대 24개 작업이고 서비스 전체 동시 실행은 기존 3개 한도를 공유한다. 모든 노드의 스키마·실행 설정을 먼저 검사·고정하므로 뒤쪽 노드가 잘못되어도 앞쪽 작업이 먼저 시작되지 않는다. `output_key`는 요청 산출물의 담당자를 하나로 정한다. 동일 task/input과 동일 선행 자료를 쓰는 중복 작업, 없는 선행 작업, 순환, 원문에 없는 `request_excerpt`, 미지원·시스템 업무 삽입을 거부한다. 같은 유형·지시문이라도 서로 다른 선행 자료를 소비하면 별도 작업으로 허용한다.

코드 작업의 독립 노드가 동일 경로를 소유하면 거부한다. 같은 파일의 연속 수정은 의존성과 정확히 같은 경로 표기가 있어야 한다. 계획 전체의 `source_files`와 `allowed_paths`에서 같은 파일을 대소문자·유니코드 정규화만 달리 표기한 경우도 접수 전에 거부한다. 파일/디렉터리 충돌은 순서와 관계없이 거부한다. 별도 결과가 아닌 긴밀한 변경은 스킬에서 하나로 합친다.

`request_excerpt` 검사는 원문에 없는 근거를 방지하지만 인용의 의미와 분할의 적절성을 완벽하게 판정하지는 않는다. 스킬의 분류 기준, 작업의 고정 경계, 선택된 독립 검토가 의미 판단을 담당한다. 코드 경로·스키마·의존성·검증 근거와 검토 생략 허용 여부는 실행 코드가 검사한다.

## 선행 산출물 전달

선행 작업은 접수 때 고정한 workflow의 필수 게이트를 통과해야 한다. 검토가 필수면 `produce → verify → review → render`와 필요한 수정·재검토를 수행한다. 생략이 허용된 단순 텍스트는 `produce → verify → render`를 수행하고 독립 검토가 있었다고 기록하지 않는다. 서비스는 후속 작업을 시작하기 직전에 선행 산출물의 관리 원본과 공개 파일의 실제 해시를 대조한다. 전이적 선행 자료도 같은 방식으로 고정하며 합계 2 MiB를 넘으면 조용히 잘라 쓰지 않고 차단한다.

CLI는 `run`·`orchestrate` 호출 시 최초 요청 에이전트의 현재 디렉터리를 `workspace`로 기록한다. 백그라운드 서비스나 worker의 임시 디렉터리를 프로젝트로 사용하지 않는다. 검증된 결과는 `<workspace>/output/worklog/<run-id>/<등록된 파일명>`에 게시하고 `artifact.output_file` 및 계획의 `artifacts[].output_file`로 반환한다. 기존 `file`은 로컬 관리 저장소의 원본 경로로 유지한다. 기존 파일 내용이 다르거나 경로가 심링크로 바뀌면 덮어쓰지 않는다. API 요청은 `workspace`를 명시할 수 있고, 생략한 기존 요청과 내부 메타데이터 작업은 로컬 관리 저장소만 사용한다.

같은 계획에서 아직 생성되지 않은 결과에는 `depends_on`을 사용한다. 별도 요청에서 기존 결과를 사용할 때는 run 또는 계획 step의 `input_files`에 실제 반환 경로와 선택적인 `content_digest`를 전달한다. 예:

```json
{
  "task": "frontend.implement",
  "input": {
    "requirements": "첨부한 FE 실행 계획에 따라 초대 화면을 구현한다.",
    "source_files": [],
    "allowed_paths": ["src/invitation.tsx"]
  },
  "input_files": [
    { "path": "output/worklog/<이전-run-id>/frontend-plan.md" }
  ]
}
```

`input_files`는 workspace 안의 기존 UTF-8 일반 파일을 가리킨다. 서비스가 접수 시 내용을 읽어 버전을 고정하므로 요청 목적과 본문을 중복 입력할 필요가 없다. 파일이 없거나 지정한 해시와 다르면 실행 전에 거부한다. 작업별 입력 스키마와 변경 허용 범위는 그대로 적용하며 파일 내용은 추가 실행 권한이 아니다. 코드 묶음의 전달이 프로젝트 반영을 의미하지 않는다.

worker에게는 시도별 입력 사본의 경로·원본 위치·해시를 전달한다. 읽기 자료는 쓰기 작업 공간 밖에 분리해 파일 검사와 혼동하지 않으며 worker가 사본을 수정하면 실패 처리한다. 원본 입력은 접수 시점의 스냅샷을 사용하고, 같은 DAG의 선행 공개 산출물이 검증 후 변경되면 후행 시작과 기존 계획 재개를 차단한다.

선행 코드 묶음은 후행 작업의 `source_files`에서 같은 경로의 오래된 내용을 대체한다. 원본·새 입력·산출물 해시는 각 실행에 고정된다. 작업자가 선행 산출물의 지시를 받아 자신의 제외 범위를 확대할 수는 없다.

후행 작업이 선행 결과의 영향을 받지 않으면 의존성을 만들지 않는다. 한 가지 분기가 실패해도 독립적으로 요청한 작업은 완료할 수 있다. 실패한 작업의 후행 작업은 미실행 상태로 차단되며 전체 계획은 완료로 표시되지 않는다. 모든 요청 결과가 각자에게 필수인 검증·검토 게이트를 통과하고 최종 해시도 일치해야 전체 완료다. 별도 산출물 사이의 모든 의미적 모순을 자동 해결하는 통합 심사나 Git 병합을 제공하는 것은 아니다.

## 상태·취소·재개

실행 DB의 `plans`, `plan_steps`가 원래 요청·고정된 자식 실행 정의·의존성·각 run 연결을 저장한다. 자식 run은 기존 `attempts`, `workflow_steps`와 증거 파일을 사용한다. 동일 idempotency key 재전송은 같은 계획을 반환하고 입력이 달라지면 거부한다.

`status|result|cancel|resume <plan-id>`는 계획 전체에 적용된다. 취소를 먼저 영속 기록해 대기 노드가 시작되지 않도록 하고 실행 중 자식의 프로세스 트리를 종료한다. 서비스가 중단되면 불확실한 작업을 interrupted로 보존하고 후행 작업을 시작하지 않는다. 재개는 기존 worker가 종료되었는지·완료 산출물 해시·고정 런타임 버전을 먼저 확인하며 완료된 분기는 다시 실행하지 않는다.

계획에 속한 자식 run의 재개 요청도 부모 계획의 복구 절차를 사용한다. GUI에서 해당 실행은 **전체 계획 재개**로 표시한다. 자식 하나만 다시 실행해 의존 작업과 상태가 어긋나게 만들지 않는다.

모든 자식은 같은 work item·원래 에이전트 세션·turn에 연결된다. 원래 세션 훅이 있는 경우 실행기가 사용자 입출력을 중복 생성하지 않고 실행 결과 이벤트를 연결한다. 원본 세션이 없는 CLI 계획에는 하나의 합성 입력·종료 이벤트만 남긴다.

## 진행 출력과 설정

CLI는 stderr에 접수·변경된 진행·종료를 짧게 내보내고 stdout에는 최종 JSON 하나만 반환한다. 예: `완료 1/3 · 진행 1 · 대기 1 · 화면 명세(검토)`. 빠른 단계는 묶어 표시하고 30초 이상 조용할 때 현재 상태를 재표시한다. 예측 백분율·작업자 전체 로그·모든 검토 의견은 기본 출력에서 제외한다.

GUI의 작업 실행 설정은 제품·프로젝트·설계·FE·BE·개발 공통·조사 문서·시스템 영역으로 묶는다. 담당 범위와 제외 범위는 읽기 전용이고 지시문·backend·model·effort만 로컬에서 바꾼다. 계획에 수락된 대기 노드도 당시 설정을 사용한다.

## 코드 결과와 검증 범위

코드 작성·테스트 작성은 `requirements`, `source_files[{path,content}]`, `allowed_paths`를 받아 `changes.json`의 `summary`, `files[{path,content}]`를 만든다. 대상 파일을 임의로 찾거나 원본 저장소에 적용하지 않는다. 삭제 작업과 임의 shell 검사 명령은 현재 계약에 없다. 범위 밖 파일, 경로 탈출·경로 충돌, 원본과 같은 결과를 거부하고 산출물 파일의 심링크 여부를 확인한다. 생성된 소스 자체는 자동 검사 중 실행하지 않는다.

JavaScript·JSON은 문법을 확인한다. `.mjs`·`.cjs`는 확장자, `.js`는 제공된 원본과 변경 묶음의 가장 가까운 `package.json`에 있는 `type`을 기준으로 검사한다. 모듈 문맥을 확정할 자료가 없으면 가능한 문법 모드를 확인하고 검사 근거에 문맥 미확정을 남긴다. TypeScript·TSX·Java 등 나머지 파일은 `syntax_not_checked`로 표시한다. 코드 묶음 내보내기 함수는 새 디렉터리만 허용하고 심링크 경로를 거부하지만, 실제 프로젝트 반영 기능으로 연결되어 있지는 않다.

실행용 `source_files`는 원문과 해시를 그대로 보존하며 로그 마스킹과 구분한다. 알려진 토큰 형식이나 `password`, `api_key`, `access_token`, `refresh_token`, `secret`에 직접 대입한 비어 있지 않은 문자열이 있는 원본은 저장 전에 거부한다. 이 제한은 문자열 placeholder에도 적용되므로 변수·환경 설정 참조를 사용하는 자료를 제공한다. 입력 폼의 초기값 같은 빈 문자열은 허용한다. 소스를 마스킹한 뒤 원본인 것처럼 실행하지 않는다.

Codex·Claude의 작업 프롬프트는 stdin으로 전달하며 원본 소스를 환경변수에 중복 넣지 않는다. 테스트용 fixture도 큰 입력은 권한 `0600`의 시도별 파일로 전달한다. 이는 입력 계약에 맞는 대형 자료가 운영체제의 인자·환경변수 크기 제한 때문에 작업자 시작 전에 실패하지 않도록 하는 처리다. API 요청 본문과 선행 산출물 전달의 크기 한도는 계속 적용한다.

프로젝트 빌드·런타임 테스트는 `not_run`, 프로젝트 반영은 `project_applied: false`로 남는다. 코드 묶음의 완료를 실제 프로젝트 동작 확인이나 배포로 표현해서는 안 된다. 등록된 하네스 자체 `checks.run`과 `verification.report`는 계획 밖의 독립적인 로컬 실행 업무이며 임의 프로젝트 검사기를 대체하지 않는다.

E2E는 실제 CLI·HTTP·SQLite·프로세스·파일과 GUI를 사용하며 모델은 fixture와 프로토콜 대역이다. 업무 내용의 실제 모델 품질은 별도 실제 사례 평가가 필요하다.

확장한 서비스 E2E 전체 실행은 첫 측정에서 약 177초였다. 검사 전용 한도를 300초로 설정해 테스트가 추가된 규모를 수용하며 모델 subprocess의 180초 한도와 분리한다. 실패·미실행 판정 기준은 유지한다.
