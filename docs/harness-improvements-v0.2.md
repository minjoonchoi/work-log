# 구현 과정에서 추출한 재사용 작업 · 0.2.0

작성일: 2026-09-17

이 문서는 0.2.0 당시의 개선·검증 기록이다. 아래 단일 작업 흐름의 제한과 테스트 개수는 그 시점을 가리킨다. 현재 복합 DAG·업무 경계는 [작업 오케스트레이션](task-orchestration.md), 전체 지원 범위는 [README](../README.md)를 따른다.

## 발견한 반복과 적용

| 실제 구현·검증 중 반복한 일 | 업무 프로필 | 재사용 작업 유형 | 적용한 규칙 |
|---|---|---|---|
| 20분 경계, 재전송, crash, 병합 사례를 행동과 기대 결과로 구체화 | `test.scenarios.plan` | `plan → verify → review`, 필요한 `repair`, 최종 전달 | `SCENARIO-001`: 요구사항 ID 연결, 필수 분류 누락, 빈 행동·기대 결과 검출 |
| 서비스 E2E와 브라우저 E2E 실행, 실패 로그 확인 | `checks.run` | 결정적 `verify` | `EVIDENCE-001`: 실제 명령·반환 코드·시각·로그 기록, 실행하지 않은 검사 구분 |
| 검증 보고서에 테스트 실행 여부와 대역/실모델 범위 구분 | `verification.report` | 결정적 `render` | 고정한 근거만 사용, 로그·원본 해시 대조, 보고서 완료와 검사 통과 분리 |

같은 역할 이름의 worker를 추가하지 않았다. 기존 PRD·목업·엔티티·텍스트 생성과 새 시나리오 설계가 같은 검토·수정 실행 흐름을 사용한다. 검사 실행과 보고서는 LLM이 필요하지 않아 로컬 코드가 수행한다.

단순한 이름 등록에 그치지 않고 자체 검증에 적용했다. `npm run verify:self`가 정상 모드의 실행·관리 서비스를 별도 프로세스로 띄우고 `checks.run`으로 실제 테스트를 실행한 다음, 해당 run을 근거로 `verification.report`를 수행한다. 두 실행은 같은 work item에 연결된다. 테스트 안에서는 fixture 검사 프로필만 사용하므로 전체 E2E가 재귀 실행되지 않는다.

## 정의와 실행 경계

- `harness/jobs.json`: 사용자 업무, 산출물, workflow, 규칙.
- `harness/task-types.json`: `plan`, `produce`, `verify`, `review`, `repair`, `render`의 실행 방식과 역할 지침.
- `harness/workflows.json`: 검토를 포함한 생성/계획, 결정적 검사, 근거 보고서의 실행 흐름.
- `harness/check-profiles.json`: 유지보수자가 등록한 Node 명령의 인자 배열, 필수 파일, 제한 시간, 검사 대상, 검증 범위.
- `src/catalog.mjs`: 정의 참조와 실행기 호환성 확인, 업무별 입력 정규화, 모델 프롬프트 구성.
- `src/process-runner.mjs`: 모델과 검사 명령에 공통으로 적용하는 stdin/파이프, 출력 제한, timeout, 취소, 자식 종료, UTF-8 보존, 실행 근거 저장.
- `src/checks.mjs`: 검사 실행, 대상 지문, 이력 보존과 보고서 변환.
- `src/scenarios.mjs`: 버전이 고정된 시나리오 산출물의 형식·참조·분류 검사.

각 run은 작업 유형·workflow·업무·규칙·스키마·검사 프로필과 런타임 지문을 고정한다. 관리 GUI는 명령과 조회 API만 사용하며 실행 규칙을 복제하지 않는다. 호환되지 않는 런타임으로 중단된 작업을 새로 실행하려 하면 기존 버전을 사용하도록 차단한다. 완료 이력 조회는 유지한다.

전체 DAG 엔진이나 임의 실행 플러그인을 구현한 것은 아니다. 지원하는 실행 흐름과 task type은 제한된 내장 처리기에 연결된다. 새 업무가 기존 형식과 흐름을 사용하면 프로필로 추가하고, 새로운 산출물 형식이면 전용 검증기를 추가한다.

## 입력 계약 예

시나리오 설계:

```json
{
  "prompt": "아래 요구사항의 E2E 시나리오를 설계해 주세요.",
  "task": "test.scenarios.plan",
  "input": {
    "requirements": [
      { "id": "SESSION-20", "text": "같은 에이전트 세션의 마지막 출력과 다음 입력이 정확히 20분 떨어지면 새 WIS를 만든다." },
      { "id": "SESSION-RECOVER", "text": "관리 서비스 재시작과 훅 재전송 후에도 원본 시각과 이벤트 중복 방지를 유지한다." }
    ],
    "categories": ["normal", "failure", "boundary", "recovery"]
  }
}
```

요구사항 배열을 생략하면 프롬프트를 `REQ-001`로 묶는다. 분류를 생략하면 위 네 가지를 사용한다. 결과는 `contracts/scenario-plan.schema.json` 형식이며, 미등록 요구사항 참조·중복 ID·빈 행동·빈 기대 결과·필수 요구/분류 누락을 자동 검사한다. 행동과 기대 결과의 의미적 타당성은 독립 검토가 판단한다. 설계 문서 자체를 테스트 실행 증거로 취급하지 않는다.

등록된 검사 실행과 보고서:

```json
{ "prompt": "서비스 E2E를 실행해 주세요.", "task": "checks.run", "input": { "profile": "harness.service-e2e" } }
```

```json
{ "prompt": "검증 보고서를 작성해 주세요.", "task": "verification.report", "input": { "run_ids": ["run-…"] } }
```

일반 프롬프트의 “E2E 검사 실행”, “검증 보고서”도 업무 유형으로 분류한다. 자연어 분류는 아직 제한된 규칙 방식이다. 보고서의 run 목록을 생략하면 명시된 work item/원본 문맥 안의 최신 검사 실행을 선택한다. 해당 문맥이 없는 독립 CLI에서는 로컬 하네스의 최신 검사 실행을 사용한다. 여러 실행을 비교하려면 run 목록을 지정한다. 다른 산출물 생성 run이나 아직 수행 중인 run은 검사 근거로 받지 않는다.

## 완료와 근거

검사 명령은 `shell=false`인 인자 배열로 실행한다. 요청 input으로 명령이나 경로를 주입할 수 없고, 모델 API 키와 실모델 opt-in 환경 변수는 검사 명령에 전달하지 않는다. 등록된 코드와 테스트는 신뢰하는 로컬 코드이며 OS 샌드박스가 추가된 것은 아니다.

각 명령의 상태는 `not_run`, `running`, `passed`, `failed`, `interrupted`, `unknown`으로 구분한다. 명령 하나가 실패해도 독립적인 나머지 필수 검사를 계속 수행한다. timeout·출력 초과는 실패, 실제 시작하지 않은 검사는 미실행이다. crash 복구 시 관찰하지 못한 종료 시각이나 성공을 만들지 않는다. 이전 PID가 살아 있으면 재시도를 겹쳐 실행하지 않는다.

실행 DB에 `check_evidence` 테이블을 추가했다. 근거 JSON은 내용 해시별 새 파일로 저장하고 최신 참조만 갱신한다. 재실행의 epoch가 바뀌어도 이전 근거 파일은 유지된다. stdout/stderr/process.json의 해시도 보존하며, 보고서 생성 시 다시 대조한다. 원본 근거나 로그가 바뀌면 생성하지 않는다.

대상 파일은 프로필의 watch 목록에서 검사 전후에 해시를 계산한다. 차이가 있으면 `source_changed`로 차단한다. 보고서 생성 시점에도 대상 지문을 대조하고, 이전 결과를 현재 소스의 통과로 바꾸지 않는다. 이는 검사 전후 비교이며 외부 편집을 잠그거나 중간에 변경 후 원복한 모든 편집을 감지하는 기능은 아니다. 같은 서비스에서 시작한 검사는 서로 겹치지 않게 직렬화한다.

보고서는 요청 시점의 근거와 시각을 고정하고 프로그램으로 렌더링한다. 실패 보고서를 정확히 만든 경우 보고서 run은 완료지만 원본 검사 run은 실패로 남는다. GUI에도 이를 구분하는 문구와 검사 결과 조회를 제공한다.

## 검증 및 적용 범위

최종 작업 트리를 배포용 **Node 22.17.0**에서 하네스 자신의 업무로 실행해 **E2E 58개(서비스·CLI·설치 48개, GUI 10개)**가 모두 통과했다. 실패·skip·flaky는 0개다. 검사와 보고서는 정상 서비스 모드에서 모델 호출 없이 실행했다. 테스트 내부의 모델 작업은 명시적인 대역이다.

| 확인 | 결과 | 기록 |
|---|---|---|
| 자체 E2E 실행 → 근거 보고서 | 통과 | `output/self-verification/2026-09-16T16-06-49.779Z/result.json`, 같은 디렉터리의 `verification.md` |
| 추가 작업과 프로세스 공통화 | 시나리오 계획/수정, 검사 실행/취소/복구, 보고서 생성 E2E 통과 | `tests/e2e/reusable-tasks.test.mjs`, `tests/e2e/cli.test.mjs` |
| 실패 근거 GUI | 버튼 접근, 검사별 판정·종료 코드, 보고서 판정 구분 통과 | `tests/ui/workflows.spec.mjs`, `output/playwright/check-evidence.png` |
| macOS 배포 | 0.2.0 재빌드·코드 서명·ZIP 생성 | `dist/WorkLog-macos-arm64.zip` |
| 번들 서비스 | 설치용 Node, 훅, 새 카탈로그, 개발 검사 미실행 처리, 서명·ZIP 확인 | `output/package-validation.json` |

시나리오 중심 E2E로 요구사항 추적·복구 분류 누락 후 수정, 등록되지 않은 요구 참조 거부, 명령 실패 후 후속 검사, 취소와 자식 종료, crash 후 unknown 및 epoch 분리, timeout·출력 제한, 미설치 검사, 소스 변경, 근거/로그 변조, CLI 자연어 진입과 보고서, GUI에서 실패 근거를 읽는 흐름을 확인한다.

실행 결과와 자동 생성 보고서는 `output/self-verification/latest.json`에서 찾는다. 이 검증은 실제 서비스·명령·DB·파일·브라우저를 통과하지만 모델 응답은 테스트 대역이다. 실제 모델을 호출하는 시나리오 설계 품질 검증은 이 실행에 포함하지 않는다.

배포 앱에 정의·실행기·GUI 기능은 포함한다. 하네스 개발 저장소의 E2E 소스나 테스트 전용 검사 프로필은 배포하지 않으므로, 배포 앱에서 개발 전용 검사를 요청하면 명시적인 미실행 근거를 남긴다. 외부 프로젝트 검사 프로필·입력 첨부·전체 코드 변경 DAG·Git 통합은 이후 범위다.
