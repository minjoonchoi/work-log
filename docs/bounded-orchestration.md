# 작업별 실행 한도와 직접 응답

작업 유형·검토 선택을 서비스가 고정된 workflow로 컴파일한다. 입력 문장이나 로컬 지시문은 workflow, 실행 횟수, 도구 한도, 필수 검증을 확대하거나 약화할 수 없다. 설정된 backend/model/effort는 새 실행 시작 시 고정한다. Codex 기본값은 모든 모델 프로필에서 `gpt-5.6-luna` / `high`이며 이 최적화는 effort를 낮추지 않는다.

| 작업 | 기본 실행 | 실패·검토 처리 |
|---|---|---|
| `session.summarize`, `text.rewrite`, `work.report.create`, `task.type.draft`, `work-item.result.summarize` | 본문 직접 생성 1회 → 서비스 저장 → 코드 검사 → 전달 | 모델 검토·자동 수정 없음. 형식 오류는 실패로 기록하고 사용자가 재생성 가능 |
| `meeting.summarize`, `progress.summarize` 및 이를 상속한 사용자 유형 | 제공된 사실을 직접 요약 1회 → 코드 검사 | 별도 검토가 명시되면 reviewed workflow 사용 |
| `document.create`, `document.share.create`, `document.update`, `document.review`, `text.generate` 및 이를 상속한 사용자 유형 | 요청한 본문·수정본·검토 보고서 직접 생성 1회 → 코드 검사 | 자동 독립 검토·수정 없음. 결과물의 별도 품질 검토를 추가로 요청한 경우에만 reviewed workflow 사용 |
| `decision.record`, `status.report`, `handoff.create` | 본문 직접 생성 → 코드 검사 → 독립 직접 검토 | 정상 2회. 지적이 있을 때만 수정·재검토 |
| PRD·설계·조사·코드·전문 검토 등 | 생성 → 검사 → 독립 검토 → 전달 | 실제 지적이 있을 때만 최대 2회 수정. 최대 모델 작업자 실행 6회 |
| 로컬 검사·검사 근거 보고서 | 등록된 코드 실행 | 모델 호출 없음 |

전문 판단이 필요한 사용자 조사 요약은 독립 검토를 유지한다. 제공된 사실만 정리하는 회의·진행 요약에 조사·제품 결정·구현을 추가하면 해당 업무로 분리해야 한다. `document.review`는 요청한 원본 검토를 한 번 수행하고 지적 보고서를 만든다. 이 결과 보고서의 추가 품질 검토는 기본 실행에 포함하지 않으며 원본을 수정할 권한도 주지 않는다. `work` 스킬은 필요한 산출물만 분할하고 서비스가 수행하는 검토·수정 단계를 별도 업무로 중복 등록하지 않는다.

## 직접 응답 계약

직접 생성 작업자는 도구로 파일을 만들지 않고 다음 최종 응답만 반환한다.

```json
{"status":"done","result":{"content":"최종 산출물 전체 본문"}}
```

JSON 산출물의 `content`는 직렬화된 JSON 문자열이다. 정보 부족·실패는 각각 `blocked`/`failed`와 `result.message`를 반환한다. `done`에 경로만 반환하거나 상태와 결과 필드가 맞지 않으면 실패한다. 서비스가 전송 스키마를 검사하고 등록 파일에 원자적으로 저장한 뒤 기존 산출물 스키마·줄 수·Jira 구역·출처 참조 검사 등을 적용한다. 기존 파일 기반 전달·후속 작업·복구 계약은 유지한다. 첨부 자료와 선행 산출물은 고정한 본문을 프롬프트에 제공하므로 작업자의 파일 읽기가 필요 없다.

직접 응답은 검토 생략과 별개다. 직접 검토자는 고정된 본문·원문·검사 근거를 입력받고 기존 `evaluations`/`issues` 계약으로 판정만 반환한다. 직접 수정자는 같은 본문과 등록 지적을 받아 수정한 전체 본문을 반환한다. [70종 실행 행렬](task-execution-matrix.md)에 업무별 호출·도구 정책을 기록한다.

실행 횟수 한도는 자동 수행 한 주기(epoch)에 적용하며, 사용자의 명시적인 재개는 새 주기다. 재개는 성공한 산출물·검사·검토 근거와 다음 단계를 보존하고 실패한 단계만 새 subprocess로 실행한다. 검토 timeout 이후 생성부터 다시 시작하지 않는다. 수정 라운드는 주기가 바뀌어도 보존하며, 소진된 수정 예산은 같은 실행 재개로 초기화할 수 없다. 후보나 검사 근거가 변경·소실되면 재개를 거부한다. 자동 resume는 하지 않는다.

도구가 필요한 설계·조사 작업자는 최대 도구 호출 24회/모델 턴 설정 25회, HTML·코드 작업자는 64회/65회를 사용한다. 직접 응답은 도구 0회/모델 턴 설정 1회다. 정책은 실행 정의와 `/catalog`, 실행 조회의 `worker_policy`에 남는다. 도구 한도 초과·프로토콜 실패를 내용 수정으로 바꿔 재호출하지 않는다. 새 실행의 모델 단계별 timeout은 1시간이며, 기존에 고정한 실행 정의와 별도 로컬 검사 시간 제한은 유지한다.

## CLI별 집행과 관측의 한계

- Codex 직접 응답은 호출별 `--ignore-user-config`, `--strict-config`, `--ephemeral`과 도구·스킬·플러그인·프로젝트 지침 제외 설정을 사용한다. 기존 `CODEX_HOME` 인증을 이용하며 사용자 설정 파일을 수정하지 않는다. 지원하지 않는 CLI 설정은 명시적으로 실패하고 일반 코딩 모드로 자동 대체하지 않는다.
- Claude 직접 응답은 `--safe-mode`, 비어 있는 `--tools`, 엄격한 빈 MCP 설정, 슬래시 명령 제외를 적용한다. managed 정책과 인증은 CLI가 유지한다. CLI의 `--max-turns`와 스트림 계측을 사용한다.
- 두 CLI의 관찰 가능한 도구 이벤트가 한도를 넘으면 해당 프로세스 트리를 중단한다. 이벤트가 도구 시작 후 도착할 수 있으므로 이 검사는 사전 권한 격리의 대체가 아니다.
- Codex `exec --json`의 `turn.started`는 사용자 턴이며 내부 모델 왕복 횟수가 아니다. 따라서 내부 모델 호출을 정확히 1회로 보장했다고 기록하지 않는다. `observed_model_turns=null`, `model_turn_limit_enforcement=not_exposed_by_cli`로 명시한다. 서비스 작업자 실행 1회와 모델 서버 요청 횟수는 다르다.

`process.json`에는 실행 정책, 관측 도구/턴 수, 최초 stdout까지의 시간, 총 subprocess 시간을 저장한다. 최초 stdout은 최초 모델 토큰과 다르다. 실제 출력 품질이나 속도 향상 수치는 실모델 재측정 없이 주장하지 않는다.

시간 초과·취소·출력량/도구 한도로 중단할 때는 소유 프로세스 그룹에 종료 신호를 보내고, 유예 시간 안에 종료되지 않으면 강제 종료한다. 부모가 먼저 종료되고 다른 프로세스 그룹으로 분리된 자식이 출력 파이프를 계속 열고 있어도 무기한 기다리지 않는다. 종료 요청 또는 부모 종료 후 최대 1초의 유예 시간을 두고 스트림을 닫아 실패를 반환한다. `process.json`의 `termination_confirmed`, `parent_exit_observed`, `stdio_closed`로 실제 확인 범위를 남긴다. 종료 미확인 시 같은 run이나 부모 계획의 재개를 차단하고, 로컬 검사의 후행 명령도 미실행으로 남긴다. DB에 결과를 저장하기 전 서비스가 중단됐으면 해당 시도의 PID·작업 경로와 일치하는 `process.json`을 대조한다. 다른 그룹으로 이탈한 후손까지 모두 종료했다고 간주하거나 새 쓰기 작업을 겹쳐 실행하지 않는다.

## 작성 큐 수정

GUI 작성은 원본 에이전트의 종류와 관계없이 작업 실행 설정의 backend를 따른다. 수동·자동 업무 메타데이터 작성 모두 유효한 종료 세션 요약을 우선하고 같은 세션의 원문을 중복 첨부하지 않는다. 열린 세션·미요약·요약 이후 바뀐 세션은 원문을 사용한다. 세션 자체를 재요약할 때는 원문을 사용한다.

자동 세션 요약은 관리 서비스가 1초마다 미요약 종료 세션과 20분 유휴한 현재 세션을 조회한다. 응답을 기다리거나 사용자 실행이 진행 중인 현재 세션은 제외한다. 대기·실행·취소 확인 대기 합계를 5개로 제한하며 실제 worker 한도 3개는 유지한다. 완료 후 다음 묶음을 처리하므로 새 프롬프트가 필요하지 않다. 같은 원문에서 실패한 작업은 주기 조회나 재시작으로 반복하지 않고 수동 재요약 또는 원문 변경이 있을 때 다시 처리한다. Work Item 설명은 문장당 120자·전체 12문장으로 코드 검사하며 상세 결과는 결과 요약 댓글의 책임이다. [작성 계약과 배치 규칙](on-demand-writing.md)을 따른다.


이력 변경·병합·수동 편집으로 낡아진 내부 작성은 취소 의도를 DB에 저장하고 해당 run을 취소한다. 서비스가 잠시 없으면 다음 tick/재시작 후 재시도한다. 사용자 요청 run은 이 취소 대상이 아니다. Jira 동기화의 네트워크 대기와 로컬 작성 큐의 잠금도 분리했다.

## 검증

`task-orchestration`, `metadata-workflow`, `review-policy`, `job-catalog` E2E는 실제 subprocess·서비스·DB·파일 전달·검사·복구를 통과한다. `writing-scheduling`은 실제 저장소와 로컬 HTTP 프로토콜 대역으로 backend 선택, 오래된 작업 취소 복구, 입력 압축, 지연된 Jira와 독립적인 제출을 검증한다. `bounded-executor`는 CLI 프로토콜 대역으로 도구·모델 턴 한도, 프로세스 종료, 미지원 옵션을 검증한다.

```sh
node --test --test-concurrency=1 tests/e2e/task-orchestration.test.mjs tests/e2e/writing-scheduling.test.mjs tests/e2e/bounded-executor.test.mjs
HARNESS_LOCAL_CODEX_PROBE=1 node --test tests/e2e/bounded-executor.test.mjs
```

선택적 Codex probe는 임시 HOME/CODEX_HOME과 로컬 HTTP 서버만 사용한다. 실제 Codex의 직접 응답 설정이 수락되고 요청에 도구가 없는지 확인하며 서버는 의도적으로 오류를 반환한다. 실모델 호출·로그인·사용자 설정 변경은 하지 않는다. 이 Mac에는 Claude CLI가 없어 Claude는 프로토콜 대역까지만 검증했다. 실제 Claude CLI의 structured-output 완료와 Codex 실제 지연 개선은 별도 검증 대상이다.


2026-09-22 검증 결과: 관련 시나리오·회귀 테스트 229개 통과(112개 + 48개 + 67개, 추가 작성 큐 시나리오 2개). 생성·검사·검토·수정, 입력 자료 전달, 자동 메타데이터, 사용자 유형, Jira 완료 요약, 취소·응답 유실·재시작 복구를 포함한다. 실모델 호출, 설치본 교체, 커밋·푸시는 수행하지 않았다.
