# 작업 유형과 책임 경계

전체 70개는 사용자 업무 63개와 시스템 업무 7개다. 작업 유형은 역할 이름이 아니라 하나의 결과와 판단 책임을 기준으로 나눈다. 업무마다 `boundary.owns`, `excludes`, `inputs`, `deliverable`, `acceptance`가 있으며 `routing`은 자연어 분류를 위한 용어·동작·우선순위를 제공한다. 전체 정의는 `harness/jobs.json`, 입력 계약은 `contracts/inputs/`, 업무별 검토 근거는 `harness/rules.json`에 있다. `harness catalog --summary`로 경계를 비교하고 `harness catalog --task <id>`로 선택한 업무의 입력 스키마·완료 기준을 확인한다.

입력 필드는 업무별 스키마를 따른다. `requirements`를 사용하는 업무에서는 해당 필드에 목표와 기준 자료를 포함하며, `document.share.create`는 `source_text`, `audience`, `purpose`를 사용한다. 허용되지 않은 필드를 추가하지 않으며, 필수 정보가 요청 본문에 이미 있으면 사용자에게 같은 내용을 다시 묻지 않고 해당 필드로 정리한다. 기준 자료가 실제로 없으면 사실을 만들지 않는다. 역할 명칭만으로 PM·PO·FE·BE 업무를 모두 실행하지 않는다.

## 분류와 분할 기준

1. 사용자가 요청한 최종 산출물과 수행 동작을 먼저 식별한다. 언급만 된 참고 자료, 부정된 동작, 예시, 코드 안의 문구는 실행 요청으로 간주하지 않는다.
2. 전용 작업 유형이 일치하면 일반 `document.create`·`text.generate`보다 먼저 선택한다. 점수만으로 비슷한 업무 여러 개를 실행하지 않는다.
3. 서로 다른 최종 산출물을 명시적으로 요청했을 때만 여러 작업으로 나눈다. 한 PRD 안의 수용 기준 요약을 이유로 `acceptance.define`을 추가하지 않는다.
4. 후속 작업이 실제로 읽는 산출물만 선행 의존성으로 연결한다. 선행 산출물이 이미 제공되면 재생성하지 않는다.
5. 읽기 전용 검토·설계·계획은 보고서를 반환한다. 수정·구현을 명시적으로 요청했을 때만 변경 작업을 별도로 생성한다.
6. 필수 결정이 없으면 가능한 독립 작업은 진행하고 해당 작업만 blocked로 남긴다. 코드 변경은 기준 파일·허용 경로가 없는 상태에서 임의 저장소 변경을 시작하지 않는다.

코드 작업의 결과는 기준 파일에 대한 구조화된 변경 묶음 `changes.json`이다. 허용 경로·기준 내용·실제 변경을 검증하며 문서 작업이 대신 코드를 수정하지 않는다. 테스트 작성은 검사 실행의 증거를 대신하지 않는다. 실제 실행 근거는 실행기가 수집한 경우에만 보고한다.

| `verification.report` · 검사 근거 보고서 | 완료된 검사 실행 증거를 모은 검증 보고서 | 검사 재실행 · 누락 증거 생성 · 자체 모델 합격 판정 | 완료된 검사 run 또는 범위 내 최신 검사 |

`task.type.draft`는 GUI에서 사용자가 설명한 업무를 승인된 템플릿의 등록 전 초안으로 작성한다. 사용자가 등록 버튼을 누르기 전에는 유형을 만들지 않는다.

`work-item.result.summarize`는 WorkLog에서 Jira 완료 상태로 변경할 때 고정한 사용자 세션의 수행 결과를 일반 댓글용 한 문단으로 작성한다. `result-summary.json`의 `{text}`만 반환하며 업무 설명·원본 이력·Jira 업무 로그를 수정하지 않는다. 원격 댓글 게시와 재시도는 관리 서비스가 담당한다. 모델 생성 1회와 형식 검사만 수행하고 실제 완료 여부·성과를 독립 검토로 보장하지 않는다.

## 오케스트레이션과 진행 출력

예를 들어 “PRD와 HTML 목업, 엔티티 설계를 만들어 줘”는 PRD → (목업, 엔티티 설계)의 세 산출물로 나눈다. 화면 상세 명세나 API 계약을 별도로 요청하지 않았으면 새 최종 산출물로 자동 추가하지 않는다. 이미 확정된 PRD가 첨부되면 목업과 엔티티만 생성한다. “PRD 검토만”은 `document.review`, “코드 검토만”은 `code.review`로 보고서만 생성하고 종료한다. “코드를 검토하고 지적을 수정해 줘”는 고정된 검토 결과를 입력으로 리뷰 반영 작업을 연결한다.

“기존 PRD와 API 설계를 참고해 유관부서에 공유할 문서 작성”은 `document.share.create` 한 작업이다. 자료로 언급된 PRD·API를 다시 만들지 않는다. PRD 신규 작성과 그 결과의 공유 문서를 둘 다 요청했다면 PRD → 업무 공유 문서의 의존성을 둔다.

사용자에게 내부 workflow 단계·모델 도구 로그를 매번 나열하지 않는다. 접수 시 업무 수와 핵심 의존성을 한 줄로, 작업 완료 시 완료 수와 다음 또는 진행 중 작업을 한 줄로 알린다. 질문·차단·실패는 필요한 결정과 함께 표시한다. 확인할 수 없는 완료율을 퍼센트로 만들지 않는다.

```text
시작 · 3개 작업: PRD 작성 → HTML 목업 · 엔티티 설계
진행 · 1/3 완료: PRD 작성 완료 · HTML 목업과 엔티티 설계 진행 중
완료 · 3/3: PRD · HTML 목업 · 엔티티 설계 [산출물]
```

모델 기반 작업의 생성·검증·독립 검토·수정은 공통 workflow를 따른다. `checks.run`과 `verification.report`는 모델 없이 등록 검사와 근거 렌더링을 각각 수행한다. 작업별 GUI 지시문은 실행 시 고정되며 책임 경계와 허용 경로를 확대할 수 없다. 현재 카탈로그는 해당 업무를 지원하는 계약과 실행 경로를 제공한다. 실제 업무 품질은 업무별 모델 평가와 프로젝트 검증 근거로 확인해야 하며 카탈로그 등록 자체가 모든 도메인의 정확도를 보장하지 않는다.

`work.report.create`는 관리 서비스가 고정한 선택 날짜의 사용자 세션 또는 검증된 부분 요약에서 업무 요약을 작성하는 내부 작업이다. 분기·반기·연간은 자료의 기간 선택이며 요약 형식은 동일하다. 본문은 업무·Jira 이슈별 배경·수행 내용·결과를 세 절(`업무 개요`, `수행 내용`, `미완료·확인 사항`)로 설명한다. 내부 산출물 `{title,body,source_refs}`의 `source_refs`로 세션·하위 부분의 누락을 검사하며 사용자 본문에 참조 목록을 넣지 않는다. 일반 `status.report`의 외부 자료 해석·신규 상태 판단을 대신하지 않으며, `create-checked`로 한 부분당 모델 생성 1회와 형식·근거 참조 검사를 수행한다. [기간 선택·연간 통합·Confluence 게시](work-reports.md)를 따른다.
