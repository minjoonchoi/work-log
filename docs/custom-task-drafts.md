# 사용자 작업 등록 초안

사용자 작업 등록은 먼저 어떤 업무를 맡길지 설명하고, 작성된 초안을 편집한 뒤 등록하는 흐름이다. 설명만으로 사용자 유형을 자동 등록하거나 설명에 적힌 본 업무를 실행하지 않는다. 기존 **직접 입력** 방식도 사용할 수 있다.

## 설명과 등록

**작업 실행 설정 → 사용자 작업 등록**에서 다음 내용을 자연어로 적는다. 입력은 최대 12,000자이며 정해진 양식을 모두 채울 필요는 없다.

- 목적과 대상: 어떤 일을 누구를 위해 수행하는가.
- 입력 자료: 어떤 정보나 문서를 받는가.
- 기대 결과: 어떤 내용을 어떤 형식으로 만드는가.
- 범위와 제외 사항: 어디까지 수행하며 무엇을 제외하는가.
- 품질 기준과 제약: 반드시 확인하거나 지켜야 할 조건은 무엇인가.

예를 들어 “팀 리더에게 공유할 주간 회의 기록을 작성한다. 회의 메모에서 결정 사항·담당자·마감일을 Markdown 문서로 정리하고, 실제 일정 변경이나 메시지 발송은 하지 않는다. 메모에 없는 정보는 확인 필요로 표시한다.”처럼 설명한다.

**등록 내용 작성**을 누르면 대기·진행 상태를 표시하고, 검사에 통과한 결과로 기반 작업 유형·이름·목적·선택 키워드·Markdown 지시문을 채운다. 사용자는 이 필드와 새 업무의 backend/model/effort를 확인하고 수정한다. **등록** 버튼이 기존 사용자 작업 등록 API를 호출한 뒤에만 카탈로그에 새 유형이 생긴다. **직접 입력**은 생성 없이 같은 등록 화면을 연다.

**요청 수정·다시 작성**은 현재 설명과 편집한 초안을 보존해 설명 화면을 연다. **초안으로 돌아가기**는 편집하던 내용을 복원한다. 새 생성을 누르면 현재 초안을 새 결과로 바꾸며, 자동으로 재생성하지 않는다. 작성 실패·범위 조정 필요·취소는 화면에 표시한다. **작성 중단**, 창 닫기, 다른 화면으로 이동한 뒤 도착한 응답은 기존 편집 화면에 적용하지 않는다.

## 생성과 검사 경계

시스템 업무 `task.type.draft`는 일반 실행 서비스의 헤드리스 작업으로 접수한다. 서비스가 등록 가능한 기본 템플릿의 담당·제외 범위, 입력, 산출물, 완료 기준과 현재 기본·사용자 업무 목록을 입력에 고정한다. 클라이언트가 임의 템플릿이나 기존 업무 목록을 제공해 검증 범위를 바꿀 수 없다.

기본값은 Codex `gpt-5.6-luna` / `high`이며 **작업 실행 설정 → 시스템 → 사용자 작업 유형 초안**에서 지시문과 backend별 모델 설정을 바꿀 수 있다. 실제 생성은 설정된 CLI 모델을 호출한다. 초안 작성 모델 설정은 이후 등록할 사용자 유형의 실행 모델을 자동 결정하지 않는다. 실행 프로필은 `metadata`, workflow는 `create-checked`이며 모델 생성 한 번 뒤 코드 검사와 결과 확정을 수행한다. 독립 모델 검토나 자동 수정 단계는 없다.

결과 `task-type-draft.json`은 다음 필드만 포함한다.

| 필드 | 의미 |
|---|---|
| `template_id` | 서비스가 제공한 기본 템플릿 하나 |
| `label` | 기존 기본·사용자 업무와 중복되지 않는 작업 이름 |
| `description` | 작업의 용도와 목적 |
| `routing_terms` | 해당 작업을 구별할 선택 키워드 1~20개 |
| `instruction` | 편집 가능한 Markdown 지시문 |

코드 검사는 JSON 스키마와 길이 제한, 제공된 템플릿 참조, 이름·키워드 중복, Markdown 구조를 확인한다. 지시문은 `## 목적`, `## 입력`, `## 범위`, `## 수행 절차`, `## 완료 기준`을 순서대로 한 번씩 포함하고 각 구역에 본문이 있어야 한다. 선택한 템플릿의 산출물과 제외 조건을 보존해야 한다. 조회할 때도 확정 산출물의 해시와 계약을 다시 확인하며, 손상되거나 검사를 통과하지 못한 결과는 등록 폼에 적용하지 않는다.

서로 다른 전문 산출물을 한 유형으로 묶거나 지원 템플릿으로 표현할 수 없는 요청은 `blocked`로 범위 조정을 안내할 수 있다. 생성 결과는 입력 스키마·새 파일 형식·실행 명령·workflow·권한을 만들지 않으며, 등록 후에도 선택한 템플릿의 입력·산출물·검증·독립 검토 계약을 상속한다. 코드 검사는 의미 품질의 독립 검토를 의미하지 않는다.

## API

GUI 관리 API는 다음 경로를 제공한다. 생성 API에는 설명과 요청 키만 전달하며 backend는 `task.type.draft`의 저장된 설정으로 선택한다.

| 요청 | 본문 | 결과 |
|---|---|---|
| `POST /api/execution-settings/custom-task-drafts` | `{ "request": "업무 설명", "idempotency_key": "custom-draft-request-001" }` | 생성 요청 접수 또는 같은 요청의 기존 상태 |
| `GET /api/execution-settings/custom-task-drafts/<id>` | 없음 | 현재 상태와 검사된 초안 |
| `POST /api/execution-settings/custom-task-drafts/<id>/cancel` | `{}` | 취소 요청 후 현재 상태 |

응답은 `{ id, status, message, draft }`다. `status`는 일반 실행 서비스의 상태를 사용하며, 완료 전에는 `draft`가 `null`이다. `completed`이면 위 다섯 필드를 가진 초안을 반환한다. 실패·범위 조정 필요·취소·중단은 `failed`, `blocked`, `cancelled`, `interrupted` 상태와 메시지로 전달한다.

`idempotency_key`는 영문·숫자·`_`·`-`로 된 8~120자 문자열이다. 같은 키와 같은 설명을 다시 전송하면 기존 실행을 조회하며, 같은 키에 다른 설명을 보내면 409로 거부한다. GUI는 응답 유실로 접수 여부가 불확실할 때 같은 키를 재사용하고, 명시적인 새 작성에는 새 키를 사용한다. 늦게 도착한 응답은 현재 요청과 화면에 속하는지 확인한 후에만 반영한다.

초안 생성·조회·취소는 `execution-settings.json`의 `custom_tasks`를 변경하지 않는다. 실제 저장은 사용자가 **등록**을 눌러 `POST /api/execution-settings/custom-tasks`를 호출할 때 기존 revision·중복·템플릿 검사를 거쳐 이루어진다. 생성 중 다른 창에서 같은 이름을 먼저 등록했다면 최종 등록 단계에서 다시 거부한다.

## 이력과 보존

초안 생성 실행과 산출물은 실행 서비스에 남지만 설정 준비만으로 새 work item이나 사용자 업무 이력을 만들지 않는다. 등록된 사용자 유형과 실행 설정은 기존 `DATA_ROOT/execution-settings.json`에 저장하며 앱 번들에 포함하지 않는다. 제거·재설치는 이 파일을 보존한다. 초안 화면을 열거나 생성에 실패한 것만으로 기존 등록·설정이 바뀌지 않는다. [사용자 작업 유형의 상속·편집·삭제](execution-profiles.md)를 참고한다.

## 검증 범위

코드 계약은 `tests/e2e/task-type-draft-contract.test.mjs`, 생성 서비스와 업무 이력 분리는 `tests/e2e/custom-task-drafts.test.mjs`, 안내·직접 입력·편집·등록·실패·재작성·늦은 응답 처리는 `tests/ui/custom-task-drafts.spec.mjs`의 검증 대상이다. 기존 사용자 유형의 실행과 제거·재설치 보존은 사용자 작업·설치 E2E 범위를 유지한다. 테스트 실행 결과와 실제 모델 품질 검증은 이 설계 문서와 별도로 확인한다.
