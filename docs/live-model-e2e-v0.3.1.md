## 실모델에서 발견한 계약 불일치

첫 실행에서는 세 업무 모두 생성과 자동 검증을 통과했지만, 검토 응답을 처리하는 단계에서 `protocol_failure`가 발생했다. 생성·검토 합계 6회 호출을 사용했다.

원인은 프롬프트와 응답 검증기가 서로 다른 규칙 목록을 사용한 것이다. 프롬프트에는 업무 규칙과 공통 `OUTPUT-001`, `SCOPE-001`이 함께 전달됐다. 실제 검토자는 이 규칙들을 모두 평가했지만, 응답 검증기는 업무에 직접 선언된 규칙만 허용했다. 테스트 대역은 업무 규칙만 반환했기 때문에 기존 테스트에서 발견하지 못했다.

수정은 카탈로그 로딩 때 공통 규칙과 업무 규칙을 중복 없이 합쳐 **유효한 규칙 목록 하나**를 확정하는 방식이다. 고정된 실행 정의, 작업 지시, 응답 검증, 재개 시 검토 근거 대조가 모두 같은 목록을 사용한다. 누락된 공통 규칙의 검토 근거도 실패로 처리한다. 필수 검증·수정 한도·산출물 검사를 생략하거나 실패 기록을 성공으로 덮어쓰지 않았다.

## 관리 이력 수집 완료 대기

실모델 산출물 검증이 끝난 직후 DB를 대조하자 실행 서비스에는 42개 이벤트가 있지만 관리 서비스에는 37개만 반영돼 있었다. 검증용 스크립트가 마지막 업무의 완료 이벤트가 수집되기 전에 두 서비스를 종료한 것이 원인이었다. 원본 outbox에 이벤트가 남아 있어 유실은 없었지만, 종료된 검증 데이터의 GUI 조회는 마지막 업무를 실행 중으로 표시했다.

검증 스크립트가 각 업무의 관리 상태와 work item session 종료까지 기다린 후 서비스를 종료하도록 수정했다. 이 동작은 CLI 프로토콜 대역을 쓰는 E2E로 검증했다. 실제 검증 데이터는 모델 실행을 막은 상태로 서비스만 재시작해 남은 이벤트를 수집했다. 추가 모델 호출은 0회이며 기존 산출물 해시는 유지됐다.

복구 후 work item 3개가 모두 완료이고 work item session 3개 모두 대기가 해제됐다. 사용자 에이전트 세션 3개와 내부 worker 6개, 이벤트 42개가 보존됐으며 미연결 출력과 수집 오류는 없다. 캘린더 API의 업무·세션 두 모드에서도 각각 시간 구간 3개를 확인했다. 근거는 [management-recovery.json](../output/live/2026-09-17T00-41-57.242Z/management-recovery.json)에 있으며 최초 실행 보고서를 덮어쓰지 않았다.

사용자가 지정한 [Jev 소개 글](https://typesafe.ai/blog/introducing-system-one-models-and-jev)의 참고 지점은 소프트웨어가 소비할 수 있는 구조화된 판단 결과다. 이 하네스에서는 요청을 `task/input`, 응답을 `status/result`로 유지한다. 실행기는 JSON의 모양뿐 아니라 해당 작업에 허용된 상태·규칙·필수 근거를 검증한 후 workflow를 전이한다. 기존 Claude/Codex 실행 어댑터를 사용하며 Jev API를 추가하지 않았다.

## 승인 호출 한도

승인 한도는 생성·검토·수정 **작업 subprocess 합계 18회**다. CLI 내부의 여러 모델·도구 왕복은 해당 작업 호출에 포함되며, 토큰 사용량은 CLI가 보고한 값으로 별도 보관한다.

재실행은 `HARNESS_LIVE_PREVIOUS_REPORT`로 이전 검증 기록을 연결한다. 이미 사용한 호출 수와 현재 배치의 호출 수를 합산한다. 각 업무를 시작하기 전에 최초 생성·검토와 최대 2회 수정·재검토를 모두 수행할 여유가 있는지 확인하고, 여유가 부족하면 `not_run`으로 남긴다. 최악의 호출 수를 예약하는 보수적인 검사이므로 남은 호출이 있어도 업무를 시작하지 않을 수 있다.

`HARNESS_LIVE_APPROVED=1`의 명시적인 opt-in을 유지하며 일반 E2E에 유료 모델 호출을 추가하지 않았다. 사용자 설정, 인증, 훅·LaunchAgent 설치도 변경하지 않았다.

## 회귀 검증과 배포 패키지

실제 서비스 경로를 사용하는 네 가지 E2E를 추가했다.

- 프롬프트에 제공한 업무·공통 규칙 전체를 검토자가 반환하면 정상 완료한다.
- 자동 파일 검사가 통과해도 필수 공통 규칙의 검토 근거가 없으면 최종 전달을 차단한다.

- 검증용 스크립트가 서비스 종료 전에 세 업무의 완료·출력 이력을 관리 DB에 반영한다. 이 테스트는 CLI 프로토콜 대역을 사용한다.
