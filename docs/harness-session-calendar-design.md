1차 구현 범위와 당시 미구현 범위는 [구현 기록](implementation-v0.1.md), 당시 검증 결과는 [검증 보고서](verification-v0.1.md)에 별도로 기록한다. 이후 변경을 포함한 현재 지원 범위는 [README](../README.md)를 따른다. 아래의 EVAL 목록은 설계상 기대 시나리오이며 모두 구현·통과했다는 뜻은 아니다.

### 1.2 설계상 기본 가정

다음 항목은 추가 요구사항을 구체화하기 위한 기본 가정이다.

- **최초 출력이 없는 경우:** 첫 입력으로 세션을 만들고, 비교 가능한 출력이 아직 없으면 후속 입력을 현재 세션에 연결한다. 입력 사이의 간격으로 출력 기준을 대체하지 않는다.
- **캘린더의 시간 의미:** 실제로 관측한 입출력의 기록 구간을 표시한다. 구간 길이는 사람의 실작업 시간이나 모델의 순수 실행 시간을 의미하지 않는다.
- **work item 표시:** 연결된 세션의 기록 구간에서 시간을 계산한다. work item 생성 시각이나 타이틀 자동 갱신 시각으로 활동 시간을 만들지 않는다.
- **병합할 대표 항목:** 기존 work item 하나를 대표 항목으로 유지한다. 처음 선택한 항목을 기본값으로 제시하고 병합 화면에서 변경할 수 있게 한다.

### 1.3 세 계층의 책임

| 계층 | 목적 | 포함하는 것 | 소유하는 결정·상태 |
|---|---|---|---|
| 하네스 정의 | 작업을 어떤 방식으로 수행할지 정의 | 업무 프로필, 공통 작업 계약, workflow, 페르소나, 허용된 skill, ruleset, 권한·반복·완료 정책 | 배포·고정된 수행 규칙의 버전 |
| 작업 실행 | 하네스 정의를 적용해 실제 업무 수행 | 프롬프트 진입, 실행기, 스케줄러, executor, claude -p·codex exec worker, 검증·검토·수정 | run·task·attempt, 실제 프로세스와 실행 상태, 검증 근거·산출물 |
| 모니터링·관리 | 수행 중이거나 완료된 업무를 기록·탐색·관리 | 시스템 훅 수집기, 이력 저장소, Work Item Session 구분, work item 병합, 캘린더, macOS 메뉴 막대 GUI | 업무 소속, 시간 윈도우, 이력·요약·표시 상태, 관리 조작 이력 |

작업 실행 계층은 실행 시작 시 고정한 하네스 정의를 읽어 작업한다. 실행 과정의 이벤트와 결과를 모니터링·관리 계층이 수집한다. 관리 계층에서 작업 취소·재개를 요청하면 실행 계층의 명령 인터페이스로 전달하고, 실행 계층이 판정한 결과를 다시 수집한다.

work item 병합, 제목 편집, 캘린더 구분은 관리 계층의 조작이다. 실제 작업 순서, 사용 엔진, 검토 반복, 완료 판정은 하네스 정의를 적용하는 실행 계층의 책임이다. 관리 화면이 작업 그래프를 독자적으로 만들거나 run·task 상태를 직접 완료로 변경하지 않는다.

설치·배포는 하나의 패키지로 제공할 수 있지만 실행 계층과 관리 계층은 독립적으로 재시작할 수 있도록 구성한다. 모니터링·관리 기능을 사용하기 위해 GUI를 열어야 하는 것은 아니며, 프롬프트 기반 작업 수행도 GUI나 관리 화면을 거치지 않는다.

## 2. 용어와 관계

| 용어 | 의미 | 식별 기준 |
|---|---|---|
| Work Item | 사용자가 얻으려는 업무 결과와 관련 이력을 묶는 상위 단위 | 관리 계층의 work item ID |
| Agent Session / 에이전트 세션 | 프롬프트를 입력하고 응답받는 도구의 실제 대화 문맥. 사용자의 대화형 진입과 하네스가 프롬프트를 전달하는 백그라운드 실행을 포함 | 엔진과 도구가 제공한 원본 세션 ID |
| Work Item Session / 세션 | work item에 속한 입출력 이력을 시간 기준으로 묶은 윈도우 | 관리 계층이 부여한 별도 세션 ID |
| Turn | 입력과 그에 대응하는 응답·중단·실패를 연결하는 단위 | 도구의 turn ID 또는 검증된 로컬 연결 |
| Event | 프롬프트 입력, 응답 출력, 도구 실행, 중단 등 하나의 수집 기록 | 원본 이벤트 키와 수집기 이벤트 ID |

한 에이전트 세션에서 여러 Work Item Session이 생길 수 있다. 하나의 Work Item Session에는 여러 입력과 출력이 포함될 수 있다. 같은 work item에는 여러 에이전트 세션에서 나온 Work Item Session이 연결될 수 있다.

사용자는 기존 Claude·Codex의 에이전트 세션에서 프롬프트로 업무를 요청한다. 실행 계층은 하네스 정의를 적용하고 필요한 작업을 `claude -p` 또는 `codex exec`의 백그라운드 에이전트 세션으로 수행한다. 각 백그라운드 세션은 자신을 실행한 run·task를 식별하고, 관리 계층이 이를 부모 work item·Work Item Session에 연결한다. GUI에서는 이 연결을 따라 실행 상태와 결과를 탐색할 수 있다. 내부 worker가 새 사용자 시간 윈도우를 생성하지 않는 규칙은 4.4절을 따른다.

수집 지연으로 업무 소속이 아직 만들어지지 않은 경우에도 실행 계층은 원본 에이전트 세션·요청·run·task 연결을 보존한다. 관리 계층은 복구 후 그 근거로 업무와 세션을 연결하며, work item의 화면용 메타데이터 생성 완료를 실제 작업 시작의 전제로 삼지 않는다.

여러 날에 걸쳐 따로 생성된 work item을 병합하면 이 소속 관계를 대표 work item으로 모은다. 병합된 항목의 Work Item Session들은 각각의 시간 윈도우와 출처를 유지한다. 캘린더에서 같은 업무로 묶어 보여 주는 것과 세션 기록 자체를 합치는 것을 구분한다.

원안에서 도구의 실제 대화를 뜻하던 `Session`과 `sessions`는 각각 `Agent Session`과 `agent_sessions`로 구분한다. 새 시간 윈도우는 `work_item_sessions`로 관리한다. 원본 훅의 `session_id`는 에이전트 세션 ID이며 Work Item Session ID로 사용하지 않는다.

`SessionStart`와 `SessionEnd`는 에이전트 세션의 생명주기를 기록한다. Work Item Session의 시작은 입력 이벤트와 20분 규칙으로 판단한다. 응답 종료, 에이전트 세션 종료, 시간 윈도우 구분, work item 완료는 각각 독립적으로 관리한다.

## 3. 입출력 수집과 일시

### 3.1 수집 지점

| 원본 이벤트 | 정규화 기록 | 본문 | 시각의 의미 |
|---|---|---|---|
| UserPromptSubmit | input | 제출한 프롬프트 | 입력 이벤트의 발생 또는 훅 관측 시각 |
| Stop | output | 제공되는 마지막 assistant 메시지 | 응답 종료 이벤트의 발생 또는 훅 관측 시각 |
| 지원되는 중단 이벤트 | turn.interrupted | 사유와 확인된 부분 출력 | 중단 관측 시각 |
| 지원되는 실패 이벤트 | turn.failed | 실패 사유와 확인된 정보 | 실패 관측 시각 |
| SessionStart / SessionEnd | agent_session.started / agent_session.ended | 에이전트 세션 생명주기 정보 | 해당 이벤트 관측 시각 |

Claude와 Codex의 공식 훅 문서는 `UserPromptSubmit`의 `prompt`, `Stop`의 `last_assistant_message`를 제공한다. Codex의 마지막 응답 본문은 없을 수 있다. 지원 필드와 예외는 설치된 엔진 버전의 어댑터에서 확인한다. [Claude Hooks](https://code.claude.com/docs/en/hooks), [Codex Hooks](https://learn.chatgpt.com/docs/hooks)

입력은 제출된 요청으로 기록한다. 이후 실행이 차단되거나 실패하더라도 원래 입력을 삭제하지 않는다. Stop이 제공하는 마지막 응답과 전체 중간 출력을 구분한다. 전체 중간 이력이 필요한 기능은 지원되는 별도 수집 경로를 사용한다.

실행 계층이 직접 실행한 백그라운드 에이전트 세션은 executor가 전달한 프롬프트와 수집한 출력·실행 상태를 근거로 기록한다. 이 작업에서는 WorkLog 수집 훅을 Node 실행 전에 건너뛰어 DB·스풀 처리로 작업을 지연시키지 않는다. 이전 수집 이력에 같은 실행의 훅·executor 기록이 함께 있으면 출처와 연결 키로 대조한다. GUI는 관리 계층이 저장한 이력을 조회하며, GUI 프로세스가 살아 있어야만 실행 로그를 수집할 수 있는 구조를 만들지 않는다.

### 3.2 시각 보존

- 원본이 신뢰할 수 있는 발생 시각을 제공하면 그 시각을 `event_at`으로 사용한다. 제공하지 않으면 훅 핸들러가 관측한 시각을 사용한다.
- 훅 관측 시각 `observed_at`과 서비스 적재 시각 `ingested_at`을 구분한다. 시간 윈도우는 `event_at`을 기준으로 계산한다.
- 저장은 UTC 기준으로 하고 GUI에서 선택한 시간대로 변환한다. 시각의 원본과 정밀도를 보존한다.
- 큐 지연 때문에 실제보다 늦은 시간에 캘린더 항목이 생기지 않도록 적재 시각으로 구간을 계산하지 않는다.
- 20분 비교는 저장된 시각의 정밀도로 수행한다. 화면에 반올림한 분 단위 값으로 판단하지 않는다.

### 3.3 연결과 중복 제거

입출력의 연결에는 엔진의 turn ID와 검증된 이벤트 관계를 사용한다. 가까운 시각의 입력과 출력을 임의로 짝짓지 않는다. 연결이 불명확한 출력은 `unresolved`로 보관하고 확인 전에는 윈도우 구분 기준으로 사용하지 않는다.

원본 이벤트 키 또는 최초 로컬 스풀에 저장한 이벤트 식별자로 재전송을 중복 제거한다. 같은 내용을 사용자가 다시 입력한 경우는 별도 이벤트다. 같은 turn에 Stop이 여러 번 발생할 수 있으므로 turn ID와 이벤트 종류만으로 모두 중복 처리하지 않는다.

기록 훅은 짧은 로컬 적재 후 반환한다. 수집 정규화, 세션 구분, 캘린더 갱신은 관리 서비스가 수행한다. 제목·설명과 세션 요약은 관리 서비스가 등록된 `text.rewrite` 작업을 실행 계층에 요청하고 검증된 결과를 저장한다. 제목·설명의 자동 작성은 기본적으로 유효한 사용자 응답 5회, 이후 요약된 종료 세션 누적 5·10·15개를 기준으로 한다. GUI의 **자동 작성 설정**에서 두 기준을 각각 정수 1~1,000으로 조정하며 SQLite에 보관한다. 명시적 WorkLog 종료 중에도 사용자 본 작업은 실행 기록을 남기고 훅은 로컬 스풀에 적재한다. 관리 서비스 재실행 시 이력을 수집한다.

## 4. 20분 기준의 세션 구분

### 4.1 기본 알고리즘

20분 비교 범위는 동일한 에이전트 세션이다. 다른 에이전트 세션의 출력은 비교 대상에 포함하지 않는다. 아래 알고리즘은 발생 순서가 확인된 사용자 입출력에 적용한다.

입력 이벤트 `I`가 발생했을 때:

1. 해당 에이전트 세션의 첫 입력이면 새 Work Item Session을 생성한다.
2. 같은 에이전트 세션에서 `I`보다 앞서 발생한, 연결이 확인된 마지막 출력 이벤트 `O`를 찾는다.
3. `O`가 있고 `I.event_at - O.event_at >= 1,200초`이면 새 세션을 생성한다.
4. 간격이 1,200초 미만이면 가장 최근 입력이 속한 현재 세션에 연결한다.
5. `O`가 없고 기존 세션이 있으면 현재 세션에 연결하고 마지막 출력 미확인 상태를 유지한다.

새 세션의 시작 시각은 해당 입력 시각이다. 이전 출력 시각에 20분을 더한 시각으로 시작점을 만들지 않는다.

현재 세션과 새 입력의 work item 소속은 대표 항목을 기준으로 비교한다. 사용자가 별도 업무로 명시적으로 전환하면 간격이 20분 미만이어도 소속을 섞지 않도록 새 세션을 시작한다. 이는 시간 기준과 별도의 업무 전환 경계다. 기존 항목의 병합은 업무 전환으로 취급하지 않으며, 그 자체로 세션을 새로 만들거나 기존 경계를 재계산하지 않는다.

출력 이벤트는 자신을 발생시킨 입력의 Work Item Session에 연결한다. 출력이 도착했을 때 가장 최근에 생성된 세션으로 무조건 배정하지 않는다. 이전 세션의 응답이 늦게 끝나면 서로 다른 세션의 기록 구간이 겹칠 수 있다.

### 4.2 적용 예

| 발생 이력 | 판정 |
|---|---|
| 09:00 첫 입력 | 세션 A 시작 |
| 09:05 출력 → 09:24:59 다음 입력 | 20분 미만이므로 A 유지 |
| 09:05 출력 → 09:25:00 다음 입력 | 정확히 20분이므로 세션 B 시작 |
| 09:05 출력 → 10:00 다음 입력 | 세션 B 시작. 09:05~10:00의 공백을 별도 활동으로 채우지 않음 |
| 09:00 입력 → 09:40 출력 → 09:50 다음 입력 | 직전 출력과 10분 차이이므로 같은 세션 유지 |
| 09:00 입력 이후 출력 없이 09:30 입력 | 비교할 출력이 없으므로 기본 가정에 따라 현재 세션 유지, 출력 미확인 표시 |
| 09:05 출력 → 09:30 입력 → 응답 전 09:31 추가 입력 | 두 입력 모두 직전 출력과 20분 이상이므로 각각 새 세션 시작 |
| 이전 입력의 출력이 새 세션 시작 후 도착 | 해당 출력은 원래 입력의 세션에 연결 |

출력 이전의 연속 입력에도 확정된 출력 간격 규칙을 각각 적용한다. 실행 중인 turn이 있다는 이유로 20분 이상인 간격을 무시하지 않는다. 이 동작은 향후 입력 간격을 함께 고려하는 정책으로 바꾸기 전까지 유지한다.

### 4.3 활동 구간과 대기

- `started_at`: 해당 세션에 속한 첫 입력 시각.
- `last_input_at`: 마지막으로 확인된 입력 시각.
- `last_output_at`: 해당 세션에 연결된 마지막 응답 종료 시각. 없으면 비어 있다.
- `activity_end_at`: 해당 세션에 속한 확인된 입출력 중 가장 늦은 시각.

출력이 끝나면 현재까지의 기록 구간을 갱신한다. 그 뒤 20분이 지났다는 이유만으로 새 세션을 생성하지 않는다. 다음 입력이 들어왔을 때 구분을 확정한다. 유휴 상태를 표시할 수 있지만, 20분의 대기 시간을 기록 구간 끝에 더하지 않는다.

응답 대기 중인 항목은 대기 상태를 표시한다. 실제 출력이 확인되기 전에는 현재 시각을 출력 종료 시각으로 저장하지 않는다. 입력 하나만 있는 구간은 시간점으로 표시하고, 클릭을 위한 최소 화면 높이는 데이터상의 지속 시간과 분리한다.

중단·실패는 별도 상태로 기록하며 그 시각을 정상 출력 시각으로 바꾸지 않는다. Stop은 관측됐지만 본문이 없는 경우에는 응답 종료 시각과 본문 누락 상태를 함께 보존한다.

### 4.4 내부 worker와 메타데이터 작업

실행 계층이 시작한 worker의 이벤트는 관리 계층에서 부모 work item·작업·Work Item Session에 연결한다. 내부 worker의 프롬프트와 결과는 사용자 활동의 20분 기준을 갱신하거나 새 사용자 세션을 만드는 입력으로 사용하지 않는다.

타이틀·설명 생성, 검토, 재시도 등 내부 작업 때문에 사용자가 쉬고 있는 동안 세션이 계속 이어지는 일이 없어야 한다. 내부 작업의 상세 이력은 연결된 세션 안에서 펼쳐 볼 수 있다.

### 4.5 늦게 도착한 이벤트와 재계산

관리 서비스는 적재 순서와 발생 순서를 구분한다. 지연된 출력이 기존 입력보다 앞선 시각에 발생했다면, 그 출력이 이후 입력의 20분 판정을 바꾸는지 확인한다.

- 원본 이벤트를 보존한 상태로 영향받는 범위의 세션 구분을 다시 계산한다.
- 세션 구분과 이벤트 연결, 캘린더 조회 결과를 한 변경 단위로 갱신한다.
- 경계가 유지되는 세션의 ID는 유지한다. 합쳐지거나 나뉜 세션에는 이전 ID와 새 결과의 연결을 남겨 기존 상세 링크를 해석할 수 있게 한다.
- 동일 입력을 재처리해도 같은 구분 결과가 나와야 한다.
- 시각과 발생 순서가 충돌하거나 순서를 확정할 수 없으면 미확인 상태로 남긴다.

구분 규칙의 버전과 1,200초 기준을 관리 계층의 세션 구분 설정으로 관리한다. 실제 업무의 실행 workflow와 구분한다. 향후 기준 변경은 기존 이력의 재구분 여부를 명시한 별도 변경으로 다룬다.

재계산은 원본 에이전트 세션의 이벤트와 당시의 명시적 업무 전환 경계를 기준으로 한다. 현재 대표 work item에 여러 이력이 모였다는 이유로 다른 에이전트 세션의 출력이나 과거에 분리한 업무 구간을 하나로 섞지 않는다.

## 5. macOS 메뉴 막대 GUI와 독립적인 프롬프트 경로

### 5.1 구성과 실행 책임

초기 GUI의 지원 플랫폼은 macOS다. 설치된 앱은 상단 메뉴 막대에서 상태와 주요 기능에 접근하는 화면과, 충분한 공간에서 업무 이력을 탐색하는 상세 창을 제공한다.

| 구성 | 책임 |
|---|---|
| 하네스 정의 묶음 | 작업 계약·workflow·skill·규칙·정책 등 실제 작업 수행 방식 제공 |
| 기존 Claude·Codex의 에이전트 세션 | 사용자의 프롬프트 요청·추가 지시·결과 확인. 실행 계층의 진입점 |
| 실행 서비스와 executor | 하네스 정의에 따른 요청 접수·오케스트레이션·검증, claude -p·codex exec 실행, 실제 실행 상태와 복구 |
| 모니터링·관리 서비스 | 훅·실행 이벤트 수집, 업무 소속과 세션 구분, 이력 저장·조회, 병합, 실행 계층에 제어 요청 전달 |
| macOS GUI 앱 | 관리 계층의 인터페이스. 메뉴 막대 접근, 업무·세션·실행 탐색, 캘린더, 병합, 지원되는 제어 요청 |

프롬프트 경로는 기존 에이전트 세션에서 실행 계층에 업무를 위임하고 진행·질문·결과를 원래 진입점으로 돌려받는다. GUI 경로는 관리 계층의 이력을 조회하고 실행 제어 요청을 실행 계층에 전달한다. 양쪽의 기록은 같은 실행 ID와 원본 에이전트 세션으로 연결되며, 관리 계층이 대표 work item·Work Item Session과의 관계를 제공한다.

worker 생성·취소·재개는 실행 서비스와 executor가 수행한다. GUI 창이나 메뉴를 열 때마다 별도 실행기 또는 worker를 시작하지 않는다. 관리 계층에 오케스트레이션을 복제하거나 GUI가 실행 레코드를 직접 수정하는 경로를 두지 않는다.

### 5.2 메뉴 막대의 빠른 접근

메뉴 막대 아이콘을 선택하면 Toolbox처럼 아이콘 아래에 빠른 패널을 연다. 알림·현재 작업·최근 업무와 이동 항목을 표시하고, 업무를 선택하면 전체 창의 해당 업무 상세를 연다. 알림은 발생 시각·원인·조치를 보여 주며 전체 창의 해당 알림으로 이동한다. 상세 이력, 전체 캘린더, 다중 선택 병합은 전체 창에서 제공한다.

| 항목 | 표시·동작 |
|---|---|
| 현재 상태 | 실행 상태 확인·이력 갱신 상태, 진행 중인 업무 수, 알림 수 |
| 진행 중인 업무 | 최근 백그라운드 실행을 업무별로 묶어 표시하고 관련 세션·작업 상세로 이동 |
| 알림 | 실행·작성·Jira 동기화 문제의 원인과 발생 시각을 표시하고 해당 알림으로 이동 |
| Work Item 목록 | 전체 목록을 열어 검색·이력 탐색·다중 선택 병합 |
| 오늘의 캘린더 | 오늘 날짜로 캘린더를 열고 일·주·월 보기로 전환 |
| 최근 업무 | 최근 사용자 활동이 있는 업무와 결과로 이동 |
| 설정·상태 확인 | 실행·관리 구성요소와 실행 도구의 연결 상태, 앱 동작 설정 확인 |
| WorkLog 종료 | 내부 요약·메타데이터 작업과 관리 서비스를 중지하고 사용자 본 작업·후속 작업은 완료까지 유지 |

메뉴 공간에 맞는 수의 항목만 표시하고 나머지는 전체 목록으로 연결한다. 업무 수와 백그라운드 에이전트 수를 혼동하지 않도록, 병렬 worker가 여러 개 있는 업무는 하나의 업무 항목 아래에 표시한다.

메뉴를 여는 동작은 저장된 상태를 조회한다. 실행 결과가 갱신되어도 사용자가 선택하지 않은 상세 창을 자동으로 전면에 띄우지 않는다.

초기 구현은 AppKit `NSStatusItem`과 `NSPopover`, 별도 WKWebView의 `/quick` 화면을 사용한다. 폭 380pt·최대 높이 600pt로 표시하며 목록만 스크롤하고 바로가기는 하단에 고정한다. 알림 3개·현재 작업 5개·최근 업무 5개를 표시하고 초과분은 더보기로 해당 목록에 연결한다. 현재 작업은 `작업 실행 중`, dispatcher가 시작하기 전인 `실행 대기`, 훅의 입력 이후 종료 기록을 기다리는 `에이전트 응답 대기`로 구분한다. 외부 프로세스가 실행 중이라고 단정하지 않는다. 내부 요약 worker는 업무 수를 늘리지 않는다. GUI에는 에이전트 프롬프트 입력·질문 감지·답변 기능을 두지 않는다.

알림은 실행 실패·차단·중단, 현재 제목·설명·세션 요약 작성 실패, Jira 이슈·업무 로그의 처리 문제를 모은다. 부가 기능 실패가 업무 전체를 차단하지 않으며 알림 수와 업무 수는 구분한다. 진행·재시도 중이거나 해결된 문제는 제외한다. **알림 지우기**는 현재 알림 버전만 숨기고 원본 이력과 실패 상태를 보존하며 새 시도의 실패는 다시 표시한다.

관리 API의 이벤트로 보이는 패널을 갱신하고 패널이 닫히면 해당 화면의 구독·폴링을 중단한다. 메뉴 막대의 업무 수는 4초 간격으로 확인한다. 관리 연결이 끊기면 마지막 확인 시각과 저장된 화면을 표시하며, 실행 서비스 연결이 끊기면 실행 중 표시를 `실행 상태 미확인`으로 바꾼다. 로그인 자동 시작은 `--background`로 메뉴 막대만 유지한다. 직접 앱을 실행하면 업무 목록의 메인 창을 열고, 우클릭 메뉴에서 전체 화면 이동과 GUI 종료를 제공한다. [구현·검증 기록](menu-bar-quick-panel.md)을 함께 관리한다.

### 5.3 상세 창의 탐색 구조

설치된 GUI는 사용자별 관리 서비스에서 work item, 세션 이력, 캘린더 데이터를 조회한다. 실제 실행 상태는 실행 계층의 이벤트 또는 지원되는 상태 조회로 대조한다.

| 화면 | 주요 내용 | 이동 |
|---|---|---|
| Work Item 목록 | 제목, 설명, 업무 상태, 최근 사용자 활동, 다중 선택과 병합 | 항목 선택 시 상세, 다중 선택 시 병합 화면 |
| Work Item 상세 | 업무 결과·산출물, 연결된 세션 목록, 세션별 시각·요약 | 세션 상세 또는 해당 날짜의 캘린더 |
| Work Item Session 상세 | 시작·마지막 기록 시각, 에이전트 출처, 입력·출력과 각각의 시각, 연결된 작업 | 원문 펼치기, 백그라운드 실행 상세, 산출물 확인 |
| 백그라운드 실행 상세 | 엔진, 진행 상태, 연결된 업무·세션·작업, 검토 결과, 필요한 로그와 산출물 | 부모 업무·세션으로 이동, 지원되는 실행 취소·재개 |
| 캘린더 | 날짜 이동, 일·주·월 전환, work item·세션 표시 단위 전환 | 항목 또는 더보기 선택 시 이력 탐색 |
| Work Item 병합 | 선택한 항목, 대표 항목과 제목·설명, 모일 세션 수·날짜 범위 | 병합 실행 후 대표 work item 상세 |
| 알림 | 현재 남은 문제, 발생 시각, 소속 업무, 원인과 필요한 조치 | 해당 작업·세션·Jira 이슈 확인, 현재 알림 지우기 |

세션 상세의 기본 이력은 수집된 **입력·출력 레코드**다. 입출력 시각 내림차순으로 40건을 읽고, 하단 접근 시 과거 기록을 추가하는 무한 스크롤을 제공한다. 같은 시각은 DB 수집 순서 내림차순으로 안정적으로 정렬한다. `UserPromptSubmit`·`Stop`의 본문, 훅 이름, 관측 시각을 보존하며 입력과 응답을 하나의 가공된 대화 카드로 합치지 않는다. 원문과 요약을 구별하며 원문이 없는 자리를 생성한 문장으로 채우지 않는다. 내부 worker·도구 실행·작업 상태 이벤트는 입출력 목록에 섞지 않는다. 훅 외 하네스 CLI에서 직접 기록된 입출력은 출처를 별도로 표시한다.

해당 세션에서 요청한 작업은 기본적으로 접힌 **연결된 작업** 영역에서 제공한다. 실행 상태·결과 메시지·선택적인 산출물과 검사 근거·취소/재개만 공통으로 표시한다. 작업 결과를 모두 전용 UI에 맞추거나 GUI 편의를 위해 모델 응답 계약을 늘리지 않는다. 지원하는 산출물은 미리보기로 열고, 새 유형도 이름·상태·텍스트 기록을 확인할 수 있다. Work item 상위의 별도 작업 실행 목록과 내부 worker 이력 영역은 두지 않는다. 내부 worker 입출력은 해당 작업의 **실행 상세**에서 요청할 때 읽는다.

상세 목록 조회에는 전체 대화 본문을 포함하지 않는다. 과거 페이지는 조회 시작 시점의 수집 상한과 `(입출력 시각, 고유 순서)` 커서를 고정한다. 새 수집 레코드는 별도 수집 커서로 따라잡고 원래 시각에 합친다. 읽던 위치·기존 페이지를 유지하고, 늦게 도착한 과거 기록도 빠뜨리지 않는다. 세션 경계 변경으로 기존 기록의 소속이 바뀌면 이전 커서를 무효화한다. 실패 시 기존 기록을 유지하고 재시도를 제공한다. [조회 API와 검증 시나리오](session-record-history.md)에 구체적인 계약을 정의한다.

실행 결과의 연결은 `origin.engine + origin.agent_session_id + origin.turn_id`와 원본 입력을 대조한다. 실행이 다른 날 끝나거나 work item이 병합되어도 요청한 세션에 유지한다. 입력이 아직 수집되지 않았거나 중복 turn으로 관계가 모호하면 **세션 연결 대기**에 보관하고 시간상 가까운 세션으로 추정하지 않는다. 나중에 원본 입력이 확인되면 해당 세션으로 이동한다. 이전 버전의 실행은 명시적인 worker parent 또는 실행 ID를 포함한 하네스 CLI 입력 이벤트로 연결을 복원한다.

제목·설명 재작성은 해당 메타데이터 영역에, 세션 요약 재작성은 해당 요약 영역에 진행·완료·실패와 **실행 상세**를 제공한다. 내부 재작성을 사용자 작업 결과로 중복 표시하거나 사용자 입력·응답 및 20분 시간 구간에 포함하지 않는다. 원본 데이터와 진단 기록은 계속 보존한다.

목록과 캘린더에는 프로젝트·work item·에이전트 출처에 대한 필터를 제공한다. 선택한 날짜와 필터는 보기 전환 시 유지한다. 제목 검색 결과에서도 관련 세션과 캘린더 위치로 이동할 수 있어야 한다.

사용자가 기록을 살펴보는 동안 새 이벤트가 들어오면 해당 항목을 갱신하되 현재 날짜, 스크롤 위치, 선택한 상세 화면을 임의로 바꾸지 않는다.

### 5.4 GUI·실행·관리 구성요소의 생명주기

| 사용자 동작·상황 | 기대 동작 |
|---|---|
| GUI 창 닫기 | 상세 창만 닫고 메뉴 막대 접근과 백그라운드 실행·기록 유지 |
| 창 닫기 또는 GUI 오류 | 실행 계층의 작업·관리 계층의 수집 유지 |
| 명시적 WorkLog 종료 | 내부 관리 작업만 취소, 사용자 본 작업은 유지, 다음 실행에서 훅 스풀 수집 |
| GUI를 다시 열기 | 기존 실행 상태와 관리 이력을 조회하고 실행을 중복 생성하지 않음 |
| GUI를 열지 않고 프롬프트 요청 | 실행 계층이 하네스 정의로 업무를 수행하고 원래 진입점으로 결과 전달 |
| 실행 상세에서 특정 작업 취소 | 관리 계층이 요청을 전달하고 실행 계층이 소유권·상태 확인 후 취소 처리 |
| 관리 서비스 중단·연결 끊김 | 실행은 유지하고 수집 자료는 로컬 스풀에 보존. GUI에 이력 갱신 지연 표시 |
| 실행 서비스 중단·연결 끊김 | 관리 이력 탐색은 유지하고 현재 실행 상태는 미확인으로 표시. 실행 계층의 복구 절차로 상태 대조 |
| macOS 로그아웃·재시작 | 실행 계층이 실행 레코드·프로세스를 복구하고 관리 계층이 수집 커서·이력을 복구 |

실행 서비스와 관리 서비스는 GUI의 수명에 종속된 자식 프로세스로만 유지하지 않고, OS가 감독하는 사용자별 백그라운드 구성요소로 운영한다. 각 역할의 중복 인스턴스를 방지하고 독립적으로 재시작할 수 있게 한다. 관리 서비스가 사용자별 이력 DB를 소유하며, 실행 서비스는 실행 복구에 필요한 자체 레코드와 이벤트 저널을 소유한다.

설치 검증은 메뉴 막대 접근, 상세 창 열기, 실행·관리 구성요소 사이의 연결, 실행 계층의 환경에서 Claude·Codex CLI 접근과 인증 상태를 포함한다. 지원할 최소 macOS 버전과 CPU 아키텍처는 배포 프로필에 명시하고 실제 설치 패키지로 확인한다.

### 5.5 실행 제어와 관찰 범위

GUI의 취소·재개는 실제 실행을 소유한 실행 계층의 명령으로 처리한다. 관리 계층은 요청 전달과 결과 표시를 담당한다. 프롬프트 경로에서 실행한 업무도 같은 권한과 상태 검사에 따라 GUI에서 관리할 수 있다. 명령 전달 직후에는 처리 요청 상태를 표시하고, 실행 계층이 확인한 상태로 갱신한다. GUI에서 수행한 명령의 결과는 원래 진입점에서도 같은 실행 상태로 조회되어야 한다.

기존 앱에서 직접 수행 중인 외부 에이전트 세션은 수집·관찰 범위를 표시한다. 해당 실행을 실행 계층이 소유하거나 지원되는 제어 경로가 확인된 경우에만 제어 기능을 제공한다. 배경 프로세스가 보인다는 이유만으로 임의의 프로세스를 종료하지 않는다.

메뉴 막대와 상세 화면은 사용자에게 업무명, 진행 상황, 결과, 필요한 조치를 우선 보여 준다. subprocess 인자와 내부 추적 ID 같은 구현 정보는 진단 상세에서 확인하도록 한다.

## 6. 캘린더의 시간 매핑

Google Calendar와 유사한 날짜 탐색과 시간 배치를 제공하되, 표시하는 내용은 로컬에 수집한 업무 이력이다.

### 6.1 Work Item Session 단위

하나의 세션을 `started_at`부터 `activity_end_at`까지의 항목으로 표시한다. 기본 표시 정보는 work item 제목, 시작 시각, 기록 구간 끝 시각, 필요한 활동 상태다. 에이전트 출처와 전체 시각은 상세에서 확인할 수 있다.

동시에 진행한 세션은 시간 겹침을 유지해 나란히 배치한다. 세션 간 겹침 때문에 원래 시각을 이동하거나 길이를 변경하지 않는다.

### 6.2 Work Item 단위

work item의 시간은 연결된 세션의 기록 구간에서 계산한다.

- 일·주 보기에서는 같은 work item의 겹치거나 맞닿은 구간을 합쳐 표시한다. 떨어진 구간 사이의 공백은 유지한다.
- 하나의 work item이 서로 떨어진 시각에 활동했다면 같은 제목의 여러 구간으로 나타날 수 있다. 각 구간을 선택하면 그 구간에 연결된 세션을 보여 준다.
- 월 보기에서는 날짜별로 같은 work item의 세션을 묶은 요약 항목을 표시한다. 첫 시작 시각과 세션 수를 우선 보여 주며 상세에서 각각의 구간을 확인한다.
- 기간 내 전체 기록 길이를 표시할 때는 겹친 구간을 한 번만 계산한다. 이를 사람의 투입 시간으로 표기하지 않는다.

예를 들어 한 work item에 09:00~09:30, 09:20~09:50, 14:00~14:20의 세션이 있으면, 일 보기의 work item 단위에서는 09:00~09:50과 14:00~14:20의 두 구간을 표시한다. 세션 단위에서는 세 항목을 각각 표시한다.

### 6.3 날짜 경계와 시간대

자정을 넘는 세션은 각 날짜에서 보이는 부분으로 나눠 그리되 같은 세션 ID를 유지한다. 날짜별 조각을 별도 세션으로 저장하지 않는다.

시간대 변경은 표시 날짜와 배치에만 영향을 준다. 20분 기준은 UTC의 실제 경과 시간으로 계산한다. 날짜 경계는 선택한 시간대의 현지 날짜를 사용하며 하루가 항상 24시간이라고 가정하지 않는다.

조회 기간과 일부라도 겹치는 구간을 포함한다. 시작 시각이 조회 기간 앞에 있는 세션도 끝부분이 기간 안에 있으면 보여 준다. 길이가 없는 시간점 항목은 그 시각이 포함되는 날짜에 표시한다.

## 7. 일·주·월 보기와 공간 제한

| 보기 | 기본 배치 | 공간이 부족할 때 | 더보기 동작 |
|---|---|---|---|
| 일 | 하루의 시간축에 항목을 배치하고 겹치는 구간을 열로 구분 | 제목을 생략하고, 읽을 수 있는 최소 너비보다 좁아지는 겹침 구간은 일부 항목을 접음 | 선택한 시간 구간의 전체 항목을 시각순 목록으로 표시 |
| 주 | 날짜별 열과 공통 시간축 | 날짜 열 너비에 맞춰 정보량과 표시 열 수를 줄이고 숨긴 항목 수 표시 | 해당 날짜·시간 구간의 전체 항목 표시 |
| 월 | 날짜 셀마다 요약 항목을 행으로 배치 | 날짜 머리글과 더보기 영역을 확보한 뒤 셀 높이에 맞는 행만 표시 | 해당 날짜의 전체 항목과 일 보기 이동 제공 |

### 7.1 표시 우선순위

시간 위치, work item 제목, 시작 시각을 우선 유지한다. 종료 시각·에이전트 출처·설명 등은 공간에 따라 상세로 옮긴다. 제목은 말줄임표로 표시하고 전체 제목은 선택·포커스·상세에서 확인할 수 있게 한다.

일·주 보기의 겹침 항목 수는 실제 표시 너비와 최소 가독 너비에서 계산한다. 최소 클릭 높이 때문에 화면상 충돌하는 짧은 구간도 배치 계산에 포함하되 저장 시각은 유지한다. 최소 한 개의 항목 또는 해당 구간의 더보기 진입점이 남아 있어야 한다.

월 보기의 표시 행 수는 실제 날짜 셀 높이에서 계산한다. 행 수를 초과하면 `+N개 더보기`를 표시한다. 창 크기를 바꾸면 표시 행 수와 N을 함께 갱신한다.

### 7.2 더보기의 일관성

- N은 현재 표시 단위와 필터를 적용한 뒤 접힌 표시 항목 수다. 원본 도구 이벤트 수나 입력 수를 세지 않는다.
- work item 단위에서는 묶인 업무 항목을, 세션 단위에서는 개별 세션 항목을 펼친다.
- 목록은 시작 시각과 안정적인 보조 정렬 기준을 사용한다. 새 이벤트가 없는데도 순서가 바뀌지 않아야 한다.
- 더보기는 긴 목록의 스크롤 또는 페이지 탐색을 제공한다. 첫 화면에 없는 항목도 모두 접근 가능해야 한다.
- 접힌 항목 수와 펼친 목록은 동일한 데이터 기준으로 계산한다. 갱신 중이면 함께 갱신하거나 갱신 상태를 표시한다.
- 항목 선택 시 관련 work item, 세션 시각, 입출력 이력으로 이어져야 한다.

키보드로 날짜 이동, 항목 선택, 더보기 열기·닫기가 가능해야 한다. 상태는 색상과 함께 텍스트로 제공하고, 전체 제목 확인을 마우스 호버에만 의존하지 않는다.

### 7.3 오늘과 현재 시각, 보기 단축키

일·주·월 보기 모두 캘린더 위에 현재 현지 날짜·요일·시각을 표시한다. 표시 기간에 오늘이 있으면 해당 날짜와 요일을 블루 계열로 강조하며 날짜 요소에 `aria-current=date`를 제공한다. 월 보기에서는 오늘 셀과 요일 머리글을, 일·주 보기에서는 오늘 날짜 머리글과 시간 열을 강조한다. 오늘이 없는 과거·미래 기간에는 잘못된 오늘 표시나 현재 시간선을 만들지 않는다.

일·주 보기의 현재 시간선과 `HH:mm` 표시는 오늘 열에만 표시하고 기존 시간축과 같은 현지 시각 좌표를 사용한다. 매분, 자정 및 앱 복귀 시 현재 표시를 갱신한다. 시계 갱신은 조회나 전체 캘린더 재생성을 요구하지 않으며 선택 날짜와 사용자의 스크롤 위치를 바꾸지 않는다. 새 기록 수집으로 항목이 바뀌어도 같은 기간의 스크롤과 유지 가능한 키보드 포커스를 보존한다. 일·주 보기를 처음 열거나 기간을 바꾸면 오늘의 현재 시각을 보이게 하고, `오늘` 버튼은 같은 날짜를 다시 눌러도 현재 시각으로 이동한다.

캘린더에서 수정 키 없이 `D`, `W`, `M`을 누르면 일·주·월 보기로 전환한다. 선택 날짜와 업무/세션 표시 단위는 유지한다. 입력창·선택 상자·편집 가능한 문맥, 열린 모달, 한글 입력 조합, 키 반복, 이미 처리된 이벤트, 다른 화면에서는 동작하지 않는다. 보기 버튼은 단축키 안내와 `aria-keyshortcuts`, 선택 상태인 `aria-pressed`를 함께 제공한다.

## 8. Work Item 병합

### 8.1 병합의 의미

병합은 사용자가 같은 업무라고 지정한 여러 work item을 하나의 대표 work item으로 모으는 동작이다. 업무는 여러 날에 걸쳐 수행될 수 있고, 서로 다른 에이전트 세션에서 만들어진 항목도 병합할 수 있다. 비슷한 제목이나 같은 폴더만으로 자동 병합하지 않는다.

| 병합 전 | 병합 후 |
|---|---|
| Work Item A: 9월 16일 Codex 에이전트 세션의 세션 A1·A2 | 대표 Work Item A 아래 A1·A2·B1·C1을 날짜순으로 탐색 |
| Work Item B: 9월 17일 Claude 에이전트 세션의 세션 B1 | B의 기존 링크는 대표 A로 연결, 원래 제목과 병합 출처 보존 |
| Work Item C: 9월 19일 다른 Codex 에이전트 세션의 세션 C1 | C의 기존 링크는 대표 A로 연결, 원래 제목과 병합 출처 보존 |

대표 항목 아래에서 이력을 한 번씩 보여 준다. 각 Work Item Session의 ID, 원본 에이전트 세션, turn·이벤트 연결, 시작·끝 시각을 유지한다. 시간 구간이 겹치거나 20분보다 가깝다는 이유로 병합 시 세션을 합치지 않는다.

관련 run·task·검토·산출물도 같은 대표 항목에서 조회할 수 있도록 소속을 연결한다. 파일이나 코드의 실제 통합은 기존 실행기의 작업 계약을 따른다. 동일 이름의 산출물이 여러 개면 출처와 버전을 구분해 보여 준다.

### 8.2 GUI 다중 선택 흐름

1. 목록의 체크박스로 두 개 이상의 서로 다른 work item을 선택한다. 현재 선택 수와 선택한 항목을 확인할 수 있게 한다.
2. 선택 작업 영역에서 **병합**을 누른다.
3. 병합 화면에 선택한 항목, 대표 항목, 병합 후 제목·설명, 모일 세션 수와 날짜 범위를 표시한다.
4. 처음 선택한 항목을 대표로 제시한다. 사용자는 선택 집합 안에서 대표를 바꾸거나 제목·설명을 편집할 수 있다.
5. **선택한 N개 업무 병합**을 실행하면 관리 서비스가 변경을 저장한다. 성공 후 대표 work item 상세로 이동하고 목록·캘린더를 갱신한다.

선택 상태가 페이지 이동으로 유지되는 경우 다른 페이지에서 선택한 항목도 선택 목록에 표시한다. 병합 화면을 열 때 선택 집합을 확정하고, 사용자가 확인하지 않은 필터 결과 전체를 포함하지 않는다. 실행 전 닫으면 변경을 적용하지 않는다.

원래 항목의 제목·설명은 병합 출처에 보존하고 검색할 수 있게 한다. 병합 조작 자체는 대표 항목의 기존 제목·설명을 유지한다. 병합된 사용자 이력이 자동 작성 기준을 충족하면 대표 항목에서 별도의 자동 작성 작업을 예약할 수 있으며 진행 상태와 결과를 표시한다. 직접 편집한 값은 자동 덮어쓰기에서 보호한다. 세션과 이벤트는 원본 식별자로 집계하며 병합만으로 같은 이력을 두 번 세지 않는다.

### 8.3 관리 서비스의 일관성 보장

병합은 GUI가 관리 서비스의 명령 API로 요청한다. 관리 서비스는 선택한 원본과 대표 항목이 여전히 유효한지 확인하고 다음 변경을 하나의 트랜잭션으로 수행한다.

- 선택한 항목들의 Work Item Session과 실행·산출물 연결을 대표 항목으로 모은다.
- 대표 외 항목에는 `merged_into` 관계를 남긴다. 기본 목록에는 대표만 표시하고 원본 기록은 보존한다.
- 원래 항목, 대표 항목, 병합 시각, 옮긴 연결을 병합 이력에 기록한다.
- 기존 항목 ID의 조회·후속 명령은 대표 항목으로 해석한다. 순환된 병합 관계는 허용하지 않는다.

병합으로 바꾸는 것은 관리 계층의 업무 소속과 조회 연결이다. 실행 계층이 이미 수행 중인 작업 그래프·입력·하네스 버전·검증 기준·프로세스 소유권은 유지한다. 실행 레코드에 남아 있는 과거 work item 참조는 관리 계층에서 대표 항목으로 해석한다.

병합 요청의 재전송에는 같은 결과를 반환하도록 요청 식별자를 사용한다. 응답을 받기 전에 관리 서비스가 재시작하더라도 일부 이력만 옮겨진 상태를 남기지 않는다. 동시에 다른 병합이 이루어져 선택 대상이 달라졌다면 최신 상태로 병합 화면을 갱신하게 하고, 확인하지 않은 추가 항목을 합치지 않는다.

이미 병합된 대표 항목을 나중에 다른 항목과 다시 병합할 수 있다. 이때 앞선 원본 ID들도 최종 대표 항목을 찾을 수 있어야 하며, 같은 세션이나 이벤트를 중복 연결하지 않는다.

### 8.4 실행 중 병합과 후속 이벤트

실행 중인 작업이 있는 work item도 이력을 보존하면서 병합할 수 있게 설계한다. 실행 중인 프로세스, task ID, attempt ID, 원본 에이전트 세션 ID는 유지한다.

원래 항목 ID를 가진 훅·worker·대기 큐의 이벤트가 병합 후 도착하면 관리 서비스가 대표 항목을 찾아 연결한다. 병합된 원본 항목을 새 활성 work item으로 되살리지 않는다. 출력은 기존 입력의 Work Item Session에 연결하고, 후속 입력의 20분 비교는 원래 에이전트 세션 안에서 계속 수행한다.

병합과 동시에 이벤트가 들어오면 어느 쪽이 먼저 저장되어도 이벤트가 최종 대표 항목 아래에 한 번만 나타나야 한다. 실행 중인 타이틀·설명 생성 작업은 병합 전 스냅샷과 소속으로 대표 항목의 최신 메타데이터를 덮어쓸 수 없다.

실행 계층이 확정한 각 실행의 진행·차단·실패·완료 상태와 검증 근거를 유지한다. 관리 계층에서 대표 항목의 표시 상태는 연결된 실행에서 다시 계산한다. 진행 중인 실행이 있으면 이를 표시하고, 미완료·차단·실패를 완료 상태로 숨기지 않는다. 병합 자체는 work item의 완료 판정 근거가 아니다.

### 8.5 캘린더와 탐색에 미치는 영향

- **세션 단위 보기:** 같은 세션이 같은 시각에 그대로 표시되고, 소속과 상세 링크가 대표 work item을 가리킨다.
- **Work Item 단위 보기:** 대표 항목의 모든 세션으로 날짜별 요약과 구간 묶음을 다시 계산한다. 여러 날의 공백을 하나의 연속 작업 시간으로 채우지 않는다.
- **일·주 보기:** 서로 다른 에이전트 세션의 겹친 시간은 세션 단위에서 유지하고, work item 단위에서만 구간 합집합으로 표현한다.
- **월 보기:** 각 날짜의 대표 항목 아래 해당 날짜 세션을 모은다. 병합 후 표시 항목 수와 더보기 개수를 함께 갱신한다.
- **상세·검색:** 병합된 원래 제목으로 검색하거나 예전 링크를 열어도 대표 항목과 해당 원본 이력을 찾을 수 있게 한다.

원래 세션과 산출물의 프로젝트 출처를 보존한다. 여러 프로젝트의 이력이 연결된 대표 항목은 해당 출처로 필터링했을 때 관련 이력을 탐색할 수 있어야 한다.

| agent_sessions | 엔진, 원본 에이전트 세션 ID, 사용자 진입·내부 worker 구분, 실행 소유자 참조, 관측한 생명주기와 수집 상태 | 관리 |
| turns 및 work item 연결 | 입력과 대응 출력의 연결, 해당 사용자 요청이 속한 work item | 관리 |
| events | 수집한 원본 식별 정보, 입출력 본문 또는 파일 참조, 발생·관측·적재 시각 | 관리 |
| 실행 상태 조회용 기록 | 실행 계층에서 받은 상태와 마지막 확인 시각, 업무·세션 연결 | 관리 |

실행 계층의 레코드는 실제 작업의 재개·취소·완료 판정에 사용하는 기준이다. 관리 DB의 실행 상태는 관측한 내용을 조회하기 위한 기록이며, 관리 DB를 수정해 실제 작업 상태를 바꾸지 않는다. 두 계층은 같은 run·task·이벤트 식별자로 내용을 연결한다.

사용자별 이력 SQLite와 관련 파일은 관리 서비스가 소유한다. 실행 계층은 해당 조회 DB의 가용성과 무관하게 실행 레코드·이벤트 저널을 로컬에 보존하고, 관리 계층은 커서를 이용해 이를 수집한다. 구체적인 실행 레코드 파일 형식은 실행기 구현에서 정한다.

원본 이벤트와 파생된 시간 윈도우를 분리한다. 같은 에이전트 세션에서 다른 work item으로 명시적으로 업무를 나누더라도 이전 이벤트를 새 업무에 일괄 재배정하지 않는다. 입력의 work item 연결을 기준으로 해당 응답과 세션을 연결한다.

명시적 work item 병합에서는 업무 소속을 대표 항목으로 모으되 원본 이벤트와 당시의 출처를 보존한다. 업무 소속의 병합과 지연 이벤트에 따른 시간 윈도우 재계산은 별개의 작업이다.

세션별 시간과 캘린더의 업무 묶음은 관리 서비스가 일관되게 계산한다. GUI는 같은 세션 구분 알고리즘을 별도로 구현하지 않는다. 화면의 크기에 따른 생략·열 배치·더보기 표시 행 수는 GUI가 계산한다.

이 데이터는 하네스 내부 추적 모델이다. worker의 최소 요청 `task/input`과 응답 `status/result`에 세션 ID나 캘린더 필드를 추가하지 않는다.

### 9.2 이벤트·조회·명령 계약

캘린더 조회는 기간, 표시 시간대, 표시 단위, 필터를 받는다. 관리 서비스는 원본 세션 참조와 실제 구간, 업무별 묶음, 상세 조회에 필요한 식별자를 반환한다.

월 보기를 위해 모든 프롬프트 본문을 한 번에 읽지 않는다. 날짜·구간·요약·개수를 먼저 조회하고, 원문은 항목 상세를 열 때 조회한다. 범위 조회용 인덱스와 목록 페이지 처리를 제공한다.

관리 서비스 재시작 후에도 같은 이벤트에서 같은 세션 경계와 캘린더 구간이 복구되어야 한다. GUI는 관리 서비스의 변경 이벤트를 구독해 영향을 받은 날짜와 항목을 갱신한다.

메뉴 막대는 알림·실행 상태·최근 업무의 가벼운 요약을 조회한다. 실제 프로세스 상태와 로그는 백그라운드 실행 상세를 열 때 실행 계층의 관측 결과로 대조한다. GUI와 프롬프트 진입점의 취소·재개 요청은 같은 실행 계층 API와 상태 전이 규칙을 사용한다.

병합 명령은 선택한 항목, 대표 항목, 선택적으로 편집한 메타데이터와 재전송 식별자를 받는다. 현재 소속과 버전을 확인한 결과를 기준으로 처리하고, 성공 시 대표 항목과 변경된 날짜 범위를 반환해 목록·상세·캘린더가 함께 갱신되도록 한다.

계층 간 연결은 다음 세 가지로 나눈다.

| 연결 | 내용 | 처리 주체 |
|---|---|---|
| 수행 정의 참조 | 고정한 업무 계약·workflow·규칙·정책 | 실행 계층이 하네스 정의를 읽어 적용 |
| 실행 관측 이벤트 | 프롬프트·응답·실행 상태·검증·산출물 참조 | 훅·실행 계층이 기록하고 관리 계층이 수집 |
| 실행 제어 요청 | 특정 run·task에 대한 취소·재개와 필요한 입력 | 관리 계층이나 프롬프트 진입점이 요청하고 실행 계층이 판정·처리 |

조회·수집 경로의 장애가 실제 작업의 성공·실패 판정을 바꾸지 않는다. 전달이 지연된 이벤트는 원래 시각과 식별자를 유지해 재전송한다. 제어 요청의 전달 여부가 불명확하면 처리 결과 미확인으로 표시하고 실행 계층에서 상태를 조회한다.

| EVAL-053 | 실행 중인 업무의 제목 편집·병합·캘린더 보기 변경 | 관리 소속·표시만 갱신, 실행의 작업 그래프·권한·하네스 버전 유지 |

| EVAL-055 | 하네스 정의 업데이트와 관리 계층 재시작 | 진행 중 실행은 고정한 정의를 사용하고, 관리 이력은 실행 이벤트로 복구 |

최종 완료 조건은 하네스 정의·작업 실행·모니터링 관리의 책임이 분리되고, macOS 메뉴 막대에서 GUI 기능에 빠르게 접근하며, 기존 에이전트 세션의 프롬프트 경로가 GUI와 독립적으로 동작하는 것이다. 관리 계층에서 실제 백그라운드 실행과 연결된 업무·세션을 탐색하고 지원되는 제어를 요청할 수 있어야 한다. 두 표시 단위의 일·주·월 캘린더에서 같은 기록을 일관되게 확인하고, 여러 날·에이전트 세션의 업무를 병합한 뒤에도 원본 이력과 후속 활동을 같은 대표 업무에서 확인할 수 있어야 한다. 숨긴 항목과 각 구성요소 재시작 후 이력에도 접근할 수 있어야 한다.

### 2026-09-19 GUI 보완

세션 이력 카드는 접힌 상태에서도 요약 제목·시간 구간과 요약하기/재요약 버튼을 표시한다. 월 캘린더는 날짜별 두 항목을 먼저 보여 주고 초과 항목은 더보기로 모은다. 일·주 캘린더는 날짜별 항목이 둘을 넘으면 날짜 머리글에 전체 목록 더보기를 제공한다. 같은 시간에 겹치는 항목의 더보기도 그 겹침 묶음에 한정하지 않고 해당 날짜 전체 목록을 모달로 연다. 모달의 항목을 선택하면 해당 업무와 세션 상세를 연다. 업무/세션 표시 단위와 자정에 걸친 시간 구간은 유지한다.

업무 목록에도 `업무별 보기 / 세션별 보기`를 제공한다. 기본값은 목록의 업무별 보기와 캘린더의 세션별 보기이며, 각 화면의 선택은 독립적으로 유지한다. 선택은 GUI 웹 문맥의 localStorage에 저장하므로 화면 전환·같은 주소의 새로고침에 유지된다. macOS 앱의 비영속 WebView나 서비스 주소가 바뀐 새 실행까지 선택을 복원하는 설정은 아니다.

세션 목록은 종료 시각 내림차순, 시작 시각 내림차순, 세션 ID 순으로 정렬한다. 요약 제목과 본문, 연결된 업무, 엔진, 관측된 시작·종료 시각을 표시한다. 요약이 없으면 첫 입력의 첫 줄을 200자 이내 제목으로 사용하고, 원문 본문은 상세에서 읽는다. 요약·소속 업무·병합 전 제목으로 검색할 수 있다. 목록과 캘린더의 세션 항목은 해당 세션을 펼쳐 입력·응답 이력으로 이동한다. 요약 변경과 새 입출력은 실시간 갱신 대상이다.

업무 병합 선택은 업무별 목록에만 제공하며 표시 단위 변경 시 기존 선택을 해제한다. 현재 작업은 업무 단위 목록을 유지하고, 알림은 업무에 연결된 개별 문제를 표시하는 별도 목록으로 제공한다. 일·주 캘린더의 업무별 표시는 같은 업무의 겹치는 기록 구간만 합치고, 떨어진 구간 사이의 공백을 작업 시간으로 채우지 않는다. 월 보기에서는 같은 날의 같은 업무를 한 항목으로 묶는다. 표시 단위 변경은 원본 세션 경계·ID·입출력 기록을 바꾸지 않는다.

### 업무 목록 정렬·필터·복수 관리

업무 목록은 사용자 세션의 관측된 마지막 입출력과 사용자 요청 실행의 갱신 시각 중 최신 시각을 기준으로 내림차순 정렬하고, 동률이면 업무 ID 순으로 표시한다. 이력이 없는 업무는 생성 시각을 사용한다. 제목·설명 편집이나 내부 요약 실행은 업무 활동 시각을 올리지 않는다. 검색은 제목·설명과 병합 전 업무의 제목·설명에 적용한다.

Jira 필터는 전체·미연결·연결됨을 제공한다. 대표 업무뿐 아니라 병합한 모든 원본 업무의 로컬 연결 기록을 확인한다. 어느 하나라도 이슈가 연결되면 연결됨이다. 생성 전송 중이거나 결과를 확인하지 못한 요청만 있으면 연결 확인 필요로 표시하며, 확실한 미연결 결과에 포함하지 않는다. 목록 조회는 Jira REST API를 호출하지 않는다. 세션 목록에서도 소속 업무의 같은 Jira 필터를 적용한다.

복수 선택은 현재 표시된 업무에 한정한다. 검색어·Jira 필터·탐색 화면·표시 단위를 바꾸면 선택을 해제하며, 실시간 갱신으로 제외된 행도 선택에서 제거한다. 병합 확인에서는 대표 업무와 합쳐질 세션 수를 보여 준다. 기존 세션 ID·입출력·시각은 그대로 유지하고 대표 업무 상세에서 모든 원본 에이전트의 이력을 확인한다.

복수 삭제는 영구 삭제가 아닌 휴지통 이동이다. 확인 화면에서 대상 제목과 세션 수를 보여 준 후 대표 업무 단위로 숨긴다. 일반 업무·세션 목록, 캘린더, 빠른 패널, 일반 상세·이력 조회에서 제외한다. 휴지통에서는 제목·설명 검색과 복수 복원을 제공한다. 삭제된 항목의 세부 이력은 복원 후 접근한다. 원본 이벤트·세션·산출물·Jira 이슈와 이미 동기화한 업무 로그는 삭제하지 않는다.

삭제는 진행 중인 사용자 요청을 취소하지 않는다. 후속 훅과 작업 결과는 보관하되 자동으로 목록에 복귀시키지 않는다. 삭제 이전에 시작한 제목·설명·요약 결과는 삭제 후에 반영하지 않으며, 즉시 복원하더라도 이전 생성 결과를 새 결과로 받아들이지 않는다. 삭제한 업무의 신규 자동 요약 및 Jira 업무 로그 전송은 중지한다. 이미 원격에 전송된 요청을 삭제 조작으로 되돌리지는 않는다.

삭제·복원은 SQLite 트랜잭션과 operation ID로 기록한다. 동일 요청의 재전송은 이전 결과를 반환하고, 뒤에 수행한 복원을 오래된 삭제 재전송으로 취소하지 않는다. 입력 배열의 일부가 잘못되면 전체 요청을 적용하지 않는다. GUI는 확인한 대표 업무 ID와 버전을 함께 전달한다. 확인창을 연 뒤 다른 창에서 병합하거나 업무가 편집되면 실행을 거부하고 다시 확인하도록 한다. API에서 별칭을 직접 지정할 때는 대표 업무 전체를 뜻하며, 병합된 세션들이 일부만 삭제되거나 복원되지 않는다. 삭제 표시와 갱신 revision은 원본 이벤트와 별도로 보관한다. 삭제·복원은 2 MiB 요청 크기 한도 안에서 한 트랜잭션으로 수행한다. 병합은 한 번에 최대 100개이며 화면에서 이를 안내한다.
