# 세션 입출력 레코드와 작업 결과 표시

작성일: 2026-09-17

## 화면의 기준

세션 이력의 입력·응답은 시스템 훅에서 수집해 DB에 기록한 레코드다. 요약 모델이나 작업 결과를 이용해 원문을 재구성하지 않는다. `UserPromptSubmit` 입력과 `Stop` 응답은 각각 독립된 행이며 본문, 종류, 입출력 관측 시각과 출처를 표시한다. 본문이 없으면 누락을 표시한다. 기존 민감정보 마스킹 정책을 유지한다.

정렬은 `event_at DESC, sequence DESC`다. 훅의 `event_at`은 훅에서 실제 관측한 UTC 시각이고 DB 적재 시각 `ingested_at`과 다르다. 같은 시각의 여러 레코드도 수집 고유 순서로 고정한다. 동일 내용을 다시 제출한 입력을 내용 기준으로 지우지 않는다. 훅 이름과 출처는 저장된 값에서 읽고, 과거 훅 기록에 이름이 없으면 입력/출력 종류로 표시한다. 직접 실행한 하네스 CLI 기록은 **하네스 기록**, 출처 정보가 없는 기존 레코드는 **수집 기록**으로 구분한다.

접힌 세션은 본문을 조회하지 않는다. 세션을 펼치면 최신 40건을 표시하고 하단에 접근할 때 40건씩 과거 기록을 추가한다. 키보드 사용과 조회 오류 복구를 위해 불러오기 버튼도 제공한다. 화면을 보고 있는 동안 새 레코드는 실제 발생 시각 위치에 반영하고 읽던 행의 화면 위치를 유지한다. 아직 읽지 않은 과거 범위에 늦게 도착한 기록은 해당 범위까지 내려갔을 때 표시한다.

## 작업 결과는 선택적인 보조 정보

**연결된 작업**은 기본적으로 접힌 영역이다. 표시 계약은 실행 메타데이터의 업무명·상태·결과 메시지·선택적인 산출물과 검사 근거다. 작업마다 결과물을 UI 전용 형태로 생성하거나 `task/input`, `status/result`에 표시용 필드를 추가하지 않는다. 결과 파일이나 전용 미리보기가 없는 업무도 상태와 기록만으로 조회할 수 있다. 새 업무 이름은 공통 표시명 등록이 없으면 등록 ID를 그대로 표시한다.

지원하는 산출물의 미리보기와 검사 결과 화면은 보조 기능이다. 어떤 업무든 반드시 시각화하거나 카드로 결과 본문을 변환한다는 보장은 두지 않는다. 모델이 반환한 구조화 결과와 내부 worker 로그는 필요할 때 **실행 상세**에서 원문으로 확인한다. 사용자 입출력·도구 이벤트·worker 입출력·`run.updated`를 섞어 하나의 대화 이력으로 만들지 않는다.

## 관리 API

기존 로컬 인증 정책을 적용한다. 아래 식별자는 전송·저장 계층의 값이며 모델 응답에 추가하지 않는다.

| 경로 | 동작 |
|---|---|
| `GET /api/items/:id?view=summary` | 대화 본문 없이 세션·작업·요약 상태와 이력 건수·최신 수집 순서·소속 버전 조회 |
| `GET /api/items/:id/history?session_id=…&limit=40` | 해당 세션의 사용자 입력·출력 최신 페이지 |
| `GET /api/items/:id/history?session_id=…&cursor=…` | 고정된 범위의 다음 과거 페이지 |
| `GET /api/items/:id/history?session_id=…&after=…` | 마지막으로 확인한 수집 순서 이후의 새 레코드; 응답 커서로 끝까지 따라잡기 |
| `GET /api/items/:id/history` | 세션에 연결되지 않은 사용자 출력의 별도 페이지 |
| `GET /api/items/:id/runs/:runId/events` | 선택한 실행의 내부 worker 기록을 상세 조회 |

페이지 응답은 `records`, `next_cursor`, `watermark`, `revision`이다. 기본 크기는 40, 허용 범위는 1~100이다. 레코드에는 원본 payload와 `uid`, `sequence`, `session_id`, `resolution`, `ingested_at`을 포함한다. `next_cursor=null`이면 해당 조회 범위의 끝이다. 외부에 노출되는 API나 모델 작업 요청 계약을 변경한 것은 아니다.

과거 조회 커서는 work item·세션·세션 소속 버전·수집 상한·마지막 정렬 키를 고정한다. 새 기록이 중간에 추가되어도 offset 밀림으로 중복·누락이 발생하지 않는다. 새 기록 조회는 수집 순서 오름차순으로 고정된 상한까지 읽고, GUI에서 기존 레코드와 ID 기준으로 합쳐 입출력 시각 내림차순으로 정렬한다. 따라서 오래된 시각의 지연 기록도 따라잡는다. 새 기록이 여러 페이지면 상한까지 모두 확인한 후 수집 위치를 갱신한다.

원본 입력이나 출력의 지연 수집으로 기존 레코드의 세션 소속이 바뀌면 `history_revisions`를 증가시킨다. 이전 커서는 409로 거절하고 화면은 최신 세션 구간으로 다시 조회한다. 단순 추가 수집은 기존 과거 페이지 커서를 무효화하지 않는다. 서비스 재시작 후에도 DB 레코드 순서와 커서는 유지한다. 다른 세션·업무에 커서를 재사용하거나 잘못된 크기를 요청하면 거절한다.

요청 중 다른 업무로 이동하면 이전 요청을 취소하고 늦은 응답을 무시한다. 조회 실패는 기존 레코드를 지우지 않으며 실패한 페이지의 재시도를 제공한다. SSE 연결 복구 시 메타데이터와 수집 커서로 누락을 확인한다. 원문 이력 조회에는 모델 호출이 없다.

## 검증 시나리오

서비스 E2E `tests/e2e/history-pages.test.mjs`는 동일 시각 122건의 순서, 고정 페이지 조회 중 신규·지연 수집, 수집 커서의 여러 페이지, 실제 훅 subprocess·재전송·재시작, 인증·커서 범위, 세션 경계 변경과 미확인 출력 재연결을 확인한다.

GUI E2E `tests/ui/history-pages.spec.mjs`는 165건의 무한 스크롤과 실시간 추가, 읽던 행의 위치, 조회 오류와 재시도, 업무 전환 시 지연 응답, 이미 펼친 세션의 경계 변경을 검증한다. 등록된 전용 표시명이 없는 작업, 도구 이벤트, 내부 worker 결과가 사용자 입출력 기록에 섞이지 않는지도 확인한다. 기존 실제 Claude/Codex 훅 수집, 서비스 재연결, 작업 취소·산출물 조회 시나리오도 유지한다.

2026-09-17 검증 결과는 **서비스 99/99, GUI 32/32**다. 새 시나리오는 서비스 4개·GUI 5개다. [첫 회귀 실행](../output/self-verification/2026-09-17T09-43-14.036Z/verification.md)에서 서비스 99개는 통과했고 GUI는 31개 통과·1개 실패였다. 접힌 세션도 전체 본문을 미리 읽는다고 가정한 기존 Jira 테스트를 실제 세션 펼치기 흐름으로 수정했다. 이후 구현 코드는 변경하지 않고 [전체 GUI 32개를 재실행해 통과](../output/self-verification/2026-09-17T09-47-47.159Z/verification.md)했다. 최초 실패 기록은 그대로 보존한다.

macOS 앱·배포 ZIP 빌드와 [번들 서비스·서명·패키지 검증](../output/package-validation.json)도 통과했다. 이 검증은 실제 사용자 훅 설정을 설치하거나 실제 Jira·OAuth·모델 서비스에 접속하지 않는다.
