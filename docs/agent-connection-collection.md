# 에이전트 중간 연결과 수집

WorkLog의 연결 설정은 **이력 수집**(시스템 훅)과 **하네스 위임**(요청 스킬)을 독립 관리한다. 하네스 연결 해제는 수집·자동 요약을 중지하지 않는다. 이력 수집 연결 직후에는 `훅 수신 대기`를 표시하고 이번 연결 시각 이후의 사용자 시스템 훅이 실제로 수집되면 `훅 수신 확인`과 마지막 관측 시각을 표시한다. 설정 화면은 주기적으로 확인하며 내부 worker나 이전 연결의 기록을 새 연결의 성공으로 표시하지 않는다. [직무별 설치와 연결](harness-packages.md)

업무 생성 기준은 첫 사용자 입력(`UserPromptSubmit`)이다. Codex·Claude를 열 때의 `SessionStart`만으로는 업무를 만들지 않는다. 아직 업무가 없는 `(engine, session_id)`의 시작·종료·도구·출력 이벤트는 DB에 보관하며, 첫 입력이 도착하면 같은 트랜잭션에서 work item·에이전트 세션을 등록하고 앞서 받은 이력도 연결한다. 첫 입력 시각부터 시간 구간을 시작하고 후속 Stop을 연결한다. 시작 훅 없이 입력이 먼저 도착해도 동일하게 처리한다. 이후 늦게 SessionStart가 도착하거나 재개·압축·훅 재전송이 발생해도 같은 업무에 연결한다. 병합된 업무는 기존 대표 항목을 유지하고 삭제한 업무를 새 훅만으로 복원하지 않는다.

연결 후 처음 받은 이벤트가 Stop이면 원문과 관측 시각만 보관하고 업무 생성은 다음 입력까지 미룬다. 이후 업무가 생겨도 대응 입력이 없는 출력은 연결 미확인 이력으로 남긴다. 수신하지 못한 입력을 만들어 내지 않으며, 늦게 실제 입력이 전달되면 확인된 관계로만 연결을 다시 계산한다. 이 상태는 서비스 재시작 후에도 유지한다. 실제 대화 시간은 수집한 이벤트의 관측 시각을 사용하며 앱 설정 변경 시각을 세션 시작으로 꾸미지 않는다.

훅 subprocess는 SQLite에 접속하지 않고 짧은 파일 쓰기로 스풀에 이벤트를 남긴다. 원본 이벤트 ID가 있으면 `hook-receipts`에 완성된 최초 관측 기록을 배타적으로 게시하며, 병렬 재전송도 같은 시각·본문·원본 turn 정보를 재사용한다. 관리 서비스가 오프라인이어도 스풀은 남는다. 입력의 로컬 turn ID는 이벤트 ID에서 결정하고, 관리 서비스가 관측 순서를 재투영해 대응 입력이 유일할 때만 출력에 연결한다. 입력이 겹치면 추측하지 않으며 늦은 이벤트가 도착하면 연결을 다시 계산한다. 기존 스풀·관측 기록은 유지하고 내부 worker 훅은 파일 쓰기 전에 제외한다.

## 에이전트 세션과 업무의 고정 연결

`(engine, session_id)`마다 최초 연결된 work item을 영속적으로 고정한다. 후속 입력·출력·실행 이벤트가 다른 업무 ID를 전달해도 새 업무를 만들거나 기존 연결을 바꾸지 않는다. 충돌한 요청 ID는 진단 정보로 보존한다. 20분 간격은 같은 업무 안의 Work Item Session만 나누며, 재개·압축·재전송·서비스 재시작도 업무를 나누지 않는다.

원본 사용자 훅보다 worker 이벤트가 먼저 도착하면 부모 에이전트 세션의 업무 연결을 먼저 예약한다. 사용자 세션이나 입력을 만들어 내지는 않는다. 병합한 업무의 후속 활동은 대표 항목에서 조회하고, 삭제한 업무는 자동 복원하지 않는다. 기존 버전에서 이미 분리된 이력은 유지하며 사용자가 GUI에서 병합할 수 있다.

이벤트 수집 시에는 변경된 세션을 갱신하고, 부모 입력의 시간 구간 연결이 실제로 달라진 턴에 대해서만 내부 세션으로 전파한다. 관계 인덱스는 기존 이력에도 적용하며, 같은 에이전트 세션에 과거 worker가 많이 쌓여 있어도 무관한 턴의 내부 이력을 매 입력마다 재처리하지 않는다. 부모보다 먼저 수집된 worker나 늦게 도착한 입력 때문에 시간 구간이 달라진 경우에는 관련 자식 이력도 다시 연결한다.

타이틀·설명·세션 요약 등 GUI 관리 작업은 `internal: true`로 요청한다. 소유 업무가 명시된 내부 실행은 그 업무의 작업 이력에 연결하고, 소유 업무가 없는 내부 요청은 runtime의 실행·산출물 기록만 남긴다. 신규 작업 유형 초안은 소유 업무와 관계없이 앱 설정 작업으로 남긴다. 사용자가 직접 요청한 업무와 GUI 내부 작업은 같은 텍스트 작업 유형을 쓰더라도 실행 소유권을 구분하며, 사용자의 작업을 유형 이름만으로 내부 작업으로 변경하거나 취소하지 않는다.

executor는 시작 전에 `runs/<run-id>/<attempt-id>/worker-context.json`에 작업 공간과 엔진·실행 소유 정보를 기록한다. 내부 훅은 우선 `HARNESS_WORKER`로 제외하며, 표식 환경 변수가 전달되지 않아도 훅의 `cwd`(없으면 프로세스 cwd)가 해당 엔진의 등록된 작업 공간 안이면 사용자 이력 수집을 생략한다. 표식은 산출물 작업 공간 밖에 두며 다른 프로젝트나 다른 엔진, 경로 이름만 같은 폴더는 제외하지 않는다. 임의의 다른 경로로 이동한 자식 프로세스까지 이 보조 판별로 식별한다고 가정하지 않는다. 내부 실행 이력은 executor가 기록하고 다른 필수 시스템 훅은 변경하지 않는다.

Codex 안에서 `harness run` 또는 `harness orchestrate`를 호출하면 `CODEX_THREAD_ID`로 관리 서비스에 원본 세션을 조회한다. 관리 서비스는 해당 세션의 대기 중인 훅 스풀을 먼저 수집하고, 종료되지 않은 실제 사용자 입력이 하나로 확인될 때만 그 origin과 work item을 전달한다. 따라서 위임 작업에 별도 하네스 업무나 가짜 입출력을 만들지 않는다. 명시적으로 전달한 origin은 그대로 사용한다.

등록된 세션의 현재 입력이 없거나 여러 개라 모호하면 제출을 중단한다. 삭제한 업무와 충돌하는 업무 지정도 중단한다. 원본 에이전트 환경이 있는 호출은 세션 미등록·관리 서비스 연결 실패·시간 초과에도 오류로 반환하며 별도 업무를 생성하지 않는다. 에이전트 안에서 호출한 하네스 작업은 기존 업무의 run/task이며 새 사용자 세션이 아니다. 원본 에이전트 환경 없이 직접 요청하는 독립 CLI 실행만 자체 진입 세션을 생성한다. worker가 부모 업무 연결만 예약한 경우도 현재 입력이 수집될 때까지 제출을 중단한다. 폴더·제목으로 원본을 추정하지 않으며, Claude 진입점은 확인된 origin을 명시적으로 전달한다.

## 에이전트의 설정 적용

Codex는 비관리 훅 정의의 정확한 해시를 신뢰하기 전에는 실행을 건너뛴다. `/hooks`에서 WorkLog 훅을 검토·신뢰한 뒤 입력을 제출한다. 공식 문서는 실행 중인 모든 Codex 환경에서 설정 파일 변경이 자동 적용된다고 보장하지 않는다. 해당 환경이 새 설정을 읽지 않으면 세션을 재개하여 적용 여부를 확인한다. WorkLog는 신뢰 승인을 자동 작성하거나 다른 필수 훅을 비활성화하지 않는다. [OpenAI Hooks](https://learn.chatgpt.com/docs/hooks)

Claude Code의 공식 문서는 설정 파일의 직접 훅 변경을 파일 감시로 보통 자동 적용한다고 설명한다. 수신되지 않으면 해당 환경의 설정 반영과 훅 활성화를 확인한다. Codex의 `/hooks` 신뢰 승인 절차를 Claude에도 동일하게 요구하지 않는다. [Claude Hooks](https://code.claude.com/docs/en/hooks#disable-or-remove-hooks)

실행 중인 앱이 훅을 호출하지 않는 상황은 WorkLog가 이벤트를 수신한 상황과 다르다. 연결 전 이력을 추정·조작하거나 프로세스 화면을 읽어 채우지 않는다. 기록은 훅이 실제로 전달한 첫 이벤트부터 시작한다.

## 검증 범위

격리된 설치 홈에서 연결 API→실제 훅 subprocess→로컬 스풀→관리 DB→GUI API를 확인한다. 시작 훅 없는 입력·출력, 연결 해제·재연결, 실제 수신 상태 표시, 중복 이벤트와 서비스 재시작을 포함한다. GUI 연결 상태와 실제 Claude/Codex 제품의 신뢰·설정 갱신은 구분하며, 테스트 대역의 수신 성공을 모든 실행 중인 앱의 자동 설정 반영으로 주장하지 않는다.

업무 식별 E2E는 첫 입력 전 업무 미생성, 첫 입력 후 하나만 생성, 같은 세션의 충돌 ID, 부모보다 먼저 도착한 worker, 병합·삭제 후 활동, 병렬 수신·재시작, 이전 분리 이력 보존을 검증한다. CLI E2E는 원본 Codex 입력→실제 CLI→fixture worker→관리 이력까지 같은 업무로 연결되는지 확인한다. Codex·Claude CLI 대역으로 자동 타이틀 생성과 세션 요약을 실행하며 내부 환경 표식이 없는 훅도 새 업무를 만들지 않는지, 일반 프로젝트의 훅은 계속 수집되는지 확인한다. 이는 다른 Mac의 실제 CLI 환경에서 원인이 확인됐다는 의미는 아니다.
