# WorkLog 자동 생성과 선택형 하네스

## 설정 화면의 역할

| 모달 | 관리하는 내용 | 화면 구분 |
|---|---|---|
| 연결 설정 | 에이전트 연결과 사용할 직무 범위 | `에이전트 연결` / `직무 패키지` 탭 |
| Atlassian 연결 설정 | OAuth 인증과 회사 네트워크 연결 | `OAuth 연결` / `네트워크·진단` 탭 |
| 작업 실행 설정 | 작업별 지시문·backend·model·effort | 기존 `WorkLog 자동 생성` / `하네스 작업` 탭 |
| 자동 작성 설정 | 제목·설명 자동 작성의 응답 수·종료 세션 수 기준 | 단일 화면 |

연결 설정의 Atlassian 바로가기는 별도 인증 모달을 열며 돌아가기로 원래 탭에 복귀한다. 작업 실행 설정에서 직무 패키지 관리를 열면 해당 탭으로 바로 이동하고 기존 편집 화면으로 돌아갈 수 있다. OAuth와 네트워크 탭을 이동해도 입력 중인 값은 유지하며 `설정 저장`은 두 탭의 변경을 함께 저장한다. 모달을 닫거나 연결 설정으로 돌아가면 저장하지 않은 인증 입력은 버리고 비밀값은 지운다. 탭은 방향키와 Home/End로 이동할 수 있다.

WorkLog의 이력 관리와 에이전트 작업 위임은 독립 기능이다. 이력 수집만 연결해도 업무·세션 탐색, 자동 제목·설명, 세션 요약을 사용할 수 있다. 하네스 위임을 해제하거나 직무 패키지를 제거해도 이 기능과 이미 수집한 데이터는 유지한다.

## 연결 설정

Claude와 Codex 카드마다 두 연결을 관리한다.

| 연결 | 추가하는 항목 | 해제 효과 |
|---|---|---|
| 이력 수집 | 해당 엔진의 WorkLog 시스템 훅 | 이후 수집 연결 제거. 기존 이력·요약 보존 |
| 하네스 위임 | `work` 요청 스킬 심링크 | 해당 엔진의 새 하네스 위임 중지. 수집 훅 보존 |

다른 프로그램의 훅·스킬은 변경하지 않는다. 두 연결은 각각의 소유 기록과 실제 파일을 비교해 상태를 표시한다. 하네스 위임 연결이 정상이어도 직무 패키지를 설치해야 그 작업을 요청할 수 있다. 원본 세션과 같은 업무에 연결하는 위임은 해당 세션의 수집된 입력도 필요하다.

업무는 첫 사용자 입력 훅을 수집할 때 생성하며, 분석 관점 선택이나 하네스 계획 접수를 기다리지 않는다. Codex의 `work` 스킬은 카탈로그 조회 후 `harness context`로 현재 `CODEX_THREAD_ID`의 업무·입력 연결을 먼저 확인한다. 이미 큐에 들어온 훅은 이 조회에서 수집할 수 있지만 원본 입력이 없으면 업무나 프롬프트를 만들어 채우지 않는다. `agent_input_unobserved`는 입력 미수집, `agent_context_unavailable`은 관리 서비스 연결 실패, `agent_identity_unavailable`은 세션 식별자 부재를 뜻하며, 모두 작업 내용 질문과 분리해서 한 번 안내한다. 이력 수집·훅 수신 또는 서비스 상태를 바로잡은 뒤 다시 확인한다.

“코드 베이스 분석해”처럼 넓은 읽기 전용 요청은 현재 저장소의 구조·진입점·흐름·의존성·테스트 구성을 기본 범위로 삼는다. 선택적인 분석 관점을 필수 질문으로 만들지 않으며, 이미 답한 질문이나 답변 대기 중인 질문은 재개 후에도 반복하지 않는다. 실제 추가 권한이나 대상을 확인해야 하는 질문은 이 규칙과 구분한다.

이미 접수된 실행과 계획의 후속 작업은 접수 당시의 정의로 계속 진행한다. 연결 해제가 이미 에이전트 문맥에 읽힌 스킬을 회수하지는 않지만, 설치 환경의 새 에이전트 위임은 서비스에서 연결 상태를 다시 확인한다. 기존 실행의 취소는 별도 실행 취소 기능을 사용한다.

`resume`은 고정된 원래 입력으로 실행을 재개하며 새 대화 답변을 전달하지 않는다. REST 재개 API도 추가 입력이 있는 요청은 거부한다. 사용자 답변으로 입력이 달라졌다면 원래 요구·기존 답변·합의한 범위를 해당 작업의 입력 스키마에 포함해 같은 업무에 새 요청으로 제출한다. 완료된 선행 산출물은 재사용하며, 동일한 차단 입력을 반복 재개하거나 이미 답한 질문을 다시 하지 않는다.

## 직무별 작업 설치

연결 설정의 직무 목록에서 필요한 묶음만 설치한다. 설치·제거는 앱에 포함된 검증된 작업 정의의 사용 여부를 변경하는 로컬 설정이다. 모델이나 추가 스킬을 다운로드하지 않으며 직무별 스킬을 복제하지 않는다.

| 패키지 | 담당 유형 |
|---|---|
| PO | 제품 문제·조사·PRD·요구사항·백로그·지표 |
| PM | 프로젝트·범위·WBS·일정·위험·진행·공유와 인수인계 |
| 프런트엔드 | HTML 목업·FE 계획과 구현·컴포넌트·UI·접근성·FE 테스트 |
| 백엔드 | 엔티티·API·BE 계획과 구현·마이그레이션·BE 테스트·쿼리 |
| 공통 | 설계·다이어그램·일반 문서와 텍스트·조사·공통 개발과 검토·검사 실행 |

여러 직무와 공통 패키지를 함께 설치할 수 있다. 패키지 선택은 같은 로컬 WorkLog를 사용하는 Claude·Codex에 공통 적용하며, 엔진별 위임 연결 여부는 별도로 유지한다. 공개 작업 하나는 한 패키지에 속하며, 직무 설치가 같은 작업 정의를 복제하지 않는다. 공통 작업이 필요하면 공통 패키지도 선택한다. 설치되지 않은 작업은 요청 카탈로그와 새 계획에서 사용할 수 없고 명시적인 task ID나 자연어 요청도 같은 정책을 따른다.

신규 설치는 직무 패키지가 없는 상태에서 시작한다. 이전 버전에서 사용하던 데이터에 패키지 설정이 없다면 기존 전체 카탈로그를 유지하며, 이후 사용자가 선택한 설치 상태를 저장한다. 앱 업데이트가 기존 선택을 바꾸지 않는다.

`work` 스킬은 일반적인 작업 요청에 자동으로 적용하되, **매 새 요청마다** `catalog --summary`를 조회해 현재 설치된 공개 작업만 계획에 사용한다. CLI 응답은 `scope: "harness"`, `package_revision`, `installed_packages`, `jobs`를 제공하며 앱 자동 생성 유형은 제외한다. `catalog --task <id>`로 상세 계약을 읽을 때도 같은 범위를 적용한다. 이전에 기억한 유형이나 문서 예시는 허용 목록을 대체하지 않는다.

설치된 유형이 없거나 요청에 맞는 유형이 없으면 하네스에 제출하지 않고 지원하지 않는 범위를 설명한다. 복합 요청의 일부가 지원되지 않으면 결과를 조용히 줄이거나 불필요한 선행 작업을 만들지 않으며, 실행 범위 변경이 필요할 때만 사용자에게 결정받는다. 조회 후 패키지가 제거되어 거부되면 카탈로그를 한 번 갱신해 현황을 알린다. 자동 재설치·다른 이름으로 우회·반복 제출은 하지 않는다. 이미 접수된 실행의 조회·멱등 재요청·단계 재개는 기존 ID와 고정된 정의를 유지한다.

## 외부 백그라운드 세션의 수집 경계

WorkLog가 실행하지 않은 Codex의 백그라운드 요청도 사용자 업무와 구분한다. 훅이 제공한 `transcript_path`의 첫 `session_meta` 레코드에서 세션 ID·CLI 버전·알려진 출처 구조를 검사한다. `exec` 또는 `subagent` 출처로 확인된 세션은 훅만으로 업무를 자동 생성하지 않는다. 따라서 직접 실행한 `codex exec`도 이 자동 수집 대상에 포함되지 않으며, 하네스로 위임한 작업 결과는 실행기가 기존 업무 아래에 별도로 기록한다. 일반 `cli`·`vscode` 대화의 같은 제목 작성 문구는 정상 수집한다.

훅은 최대 256 KiB 안의 메타데이터만 확인하고 출처 식별값만 큐에 보존한다. 전체 대화나 지시문은 출처 판별에 사용하지 않는다. 확인된 백그라운드 세션 ID는 재시작 후에도 유지하지만 하위 에이전트가 공유하는 부모 ID에는 적용하지 않는다. 경로 누락·포맷 변경·ID 불일치로 출처를 확인하지 못하면 일반 입력을 임의로 버리지 않는다. transcript 형식은 안정된 API가 아니므로 이런 경우에는 실제 훅과 세션 메타데이터를 대조해야 한다. 기존 잘못 생성된 업무는 자동 삭제하지 않는다. [Codex 훅 문서](https://learn.chatgpt.com/docs/hooks)

Claude는 훅이 상속한 `CLAUDE_CODE_ENTRYPOINT`가 `sdk-cli`·`sdk-ts`·`sdk-py`이면 비대화형 실행으로 식별한다. `sdk-cli`는 Anthropic 배포 CLI 2.1.37에서 `-p`/`--print`를 포함한 비대화형 실행에 지정하는 값으로 확인했다. 이는 공개 훅 스키마의 보장된 필드가 아니므로 값이 없거나 다른 값이면 추정해서 제외하지 않는다. 이미 출처가 확인된 세션은 이후 훅의 환경 변수가 빠져도 관리 서비스가 재식별한다. 직접 실행한 `claude -p`도 새 업무를 자동 생성하지 않으며, WorkLog 실행 결과는 기존과 같이 부모 업무에 기록한다.

Claude 하위 에이전트는 공식 훅의 `agent_id`로 해당 이벤트만 제외한다. 부모 `session_id`를 백그라운드 세션으로 등록하지 않는다. `agent_type`만 있는 경우는 `claude --agent`로 시작한 사용자 대화일 수 있으므로 제외하지 않는다. 일반 `cli`·`claude-vscode`·`local-agent` 출처와 출처 미확인 대화는 수집을 유지한다. [Claude 훅 공통 입력 필드](https://code.claude.com/docs/en/hooks#common-input-fields)

## 자동 생성 작업 설정

작업 실행 설정은 **WorkLog 자동 생성**과 **하네스 작업**으로 나뉜다. WorkLog 자동 생성에는 앱이 사용하는 다섯 유형이 있다.

| 유형 | 용도 |
|---|---|
| `session.summarize` | 세션 요약 |
| `text.rewrite` | 업무 제목·설명과 세션 요약 재작성, 자동 메타데이터 갱신 |
| `work.report.create` | 선택 기간의 업무 요약 |
| `work-item.result.summarize` | Jira 완료 결과 요약 댓글 본문 |
| `task.type.draft` | 사용자 작업 유형 등록 전 초안 |

이 그룹에는 자동 예약과 GUI 버튼으로 요청하는 생성 작업이 모두 포함된다. 각 지시문·backend·model·effort는 기존과 같이 개별 설정하며, 자동 생성 기준 횟수는 자동 작성 설정에서 관리한다. 패키지 설치 여부가 이 다섯 작업을 비활성화하지 않는다. 사용자 요청을 처리하는 일반 `text.generate`는 공통 하네스 작업이다.

자동 생성 유형은 요청의 `internal` 표시가 빠지거나 `false`여도 실행기가 작업 정의를 기준으로 내부 실행으로 처리한다. 연결된 업무가 있으면 그 업무의 실행 기록으로 남기고, 업무 연결이 없는 내부 실행은 런타임에만 기록한다. 일반 업무 목록이나 사용자 세션을 새로 만들지 않는다. 내부 작업의 네이티브 훅은 실행기에서 등록한 작업 공간으로 식별하며, 관리 서비스도 큐에 남은 훅을 업무 등록 전에 다시 확인한다. 제목이나 프롬프트 문구만으로 일반 사용자 업무를 제외하지 않는다.

하네스 작업 목록은 설치된 유형만 표시하며 **작업 유형 검색**에서 이름·ID·목적 등으로 목록을 좁힐 수 있다. 이 화면에서 **직무 패키지 관리**를 열었다면 **작업 실행 설정으로 돌아가기**로 복귀한다. 패키지를 제거한 기본 유형과 사용자 등록 유형은 목록에서 숨긴다.

사용자 등록 유형은 템플릿의 패키지를 따른다. 패키지를 제거해도 등록 내용과 지시문·모델 설정은 남고, 다시 설치하면 목록에서 같은 유형을 확인하고 편집할 수 있다. 새 유형과 초안의 템플릿 후보는 설치된 유형만 제공한다. 사용자 유형 삭제는 별도 명시적 삭제 동작이다.

## 저장과 API

`DATA_ROOT/harness-packages.json`에 형식 버전·revision·설치된 패키지 ID를 보관한다. `execution-settings.json`에는 기존 사용자 유형과 실행 설정을 유지한다. 두 파일과 업무 이력은 `make uninstall` 후에도 보존하며 재설치 시 재사용한다.

실행 설정 API는 미설치 유형을 포함한 전체 정의와 저장 설정을 계속 반환한다. GUI가 설치 여부에 따라 목록을 제한하며, 화면에서 숨기는 동작이 정의나 설정을 삭제하지 않는다.

- `GET /api/agent-connections`: 엔진별 `tracking`, `harness` 연결 상태와 실제 훅 수집 상태 조회.
- `POST|DELETE /api/agent-connections/:engine/tracking`: 이력 수집 연결·해제. 본문 `{}`.
- `POST|DELETE /api/agent-connections/:engine/harness`: 하네스 위임 연결·해제. 본문 `{}`.
- `GET /api/harness-packages`: 패키지별 설치 여부·유형 목록·revision 조회.
- `PUT /api/harness-packages/:id`: `{ "installed": true, "revision": 0 }` 형태로 변경. 오래된 revision은 충돌로 거부.

이전 엔진 단위 연결 API는 두 연결을 함께 변경하는 호환 경로로 남긴다. GUI는 분리된 API를 사용한다. 모든 API는 기존 로컬 서비스 인증을 적용한다. 패키지 변경은 외부 에이전트 설정이나 Jira 데이터를 수정하지 않는다.
