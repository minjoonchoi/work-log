# 구조화 입력과 오케스트레이션 · 0.3.0

작성일: 2026-09-17

이 문서는 0.3.0의 단일 업무 상태 기계 도입 기록이다. 아래의 복합 DAG 미지원과 당시 검증 개수는 이 버전에 대한 설명이다. 이후 추가된 작업 분할·병렬 분기·합류·계획 복구는 [현행 작업 오케스트레이션](task-orchestration.md), 지원 업무는 [카탈로그](job-catalog.md)를 따른다. 동적 재계획과 Git 통합은 현재도 후속 범위다.

## 설계 결정

하네스가 수락한 구조화 입력, 고정된 실행 정의, 검증된 단계 결과에 따라 실행 경로를 결정한다. 모델은 개별 작업을 수행하고 제한된 결과를 반환한다. 실행 순서·재시도 범위·필수 검사·최종 완료 판정은 실행 코드가 집행한다.

0.2에서는 workflow가 단계 이름을 제공하고 실행기의 고정 분기가 순서를 결정했다. 0.3에서는 `initial`, `nodes`, `on`, `max_steps`를 실행기가 해석한다. 잘못된 정의는 작업을 받기 전 차단하며, 실제 전이는 DB에 저장한다. GUI는 기존처럼 조회·관리만 담당한다.

사용자가 지정한 참고 자료는 [TypeSafe AI의 Jev 소개](https://typesafe.ai/blog/introducing-system-one-models-and-jev)다. 글은 제한된 타입의 판단 결과를 소프트웨어가 받아 분기하는 방식을 설명한다. 이 설계에 반영할 요구사항은 **JSON 방식의 요청·응답 계약과 그 결과를 소비하는 명시적인 오케스트레이션**으로 확정했다. 작업자는 `task/input`을 받아 `status/result`를 반환하고, 메인이 스키마·규칙·전이 조건을 검사한다. 실행 엔진은 기존 Claude/Codex 어댑터를 사용하며 Jev API 연동은 이 요구사항에 포함하지 않는다.

## 입력을 실행 전에 확정

요청 경로는 다음과 같다.

`자연어 또는 구조화 요청 → 업무 결정 → 업무별 입력 정규화 → 스키마 검증 → 입력·정의 고정 → 실행`

| 계층 | 계약 | 책임 |
|---|---|---|
| 실행 요청 | `contracts/run-request.schema.json` | 자연어 또는 `task/input`, 선택적 엔진·원본 세션·work item 연결 |
| 공통 작업 요청 | `contracts/task-request.schema.json` | 모델에 전달하는 최소 `task/input` |
| 업무 입력 | `contracts/inputs/*.schema.json` | 필수 자료, 허용 필드, 타입·범위 |
| 작업 응답 | `contracts/task-result.schema.json`와 작업별 결과 검사 | `status/result` 형식, 규칙 연결, 통과 근거 |
| 실행 정의 | `contracts/workflow.schema.json`와 그래프 검사 | 지원 작업, 전이 대상, 필수 게이트, 반복 제한 |

스키마는 서비스 시작 시 컴파일한다. 타입 자동 변환, 알 수 없는 필드의 자동 삭제, 스키마에 의한 암묵적 기본값 삽입을 사용하지 않는다. 업무에서 정한 기본값은 정규화 단계에서 명시적으로 확정한다. 예를 들어 시나리오 분류는 업무 정의의 기본 분류를 사용하고, 보고서의 생략된 대상은 실제 검사 run 목록으로 확정한 뒤 저장한다. 검증에는 [Ajv](https://ajv.js.org/guide/getting-started.html)를 사용한다.

```json
{
  "task": "test.scenarios.plan",
  "input": {
    "requirements": [
      {
        "id": "SESSION-20",
        "text": "같은 에이전트 세션의 마지막 출력과 다음 입력이 정확히 20분 떨어지면 새 work item session을 만든다."
      }
    ],
    "categories": ["normal", "failure", "boundary", "recovery"]
  }
}
```

이 요청은 자유 형식 `prompt` 없이 실행할 수 있다. `prd.create`, `entity.design`, `text.generate`는 문자열 `requirements`가 필수이고, HTML은 여기에 구조화된 브라우저 검사 조건을 추가할 수 있다. `checks.run`은 등록된 `profile`, `verification.report`는 검사 `run_ids`를 사용한다. `/catalog`가 업무별 스키마를 제공한다.

자연어만 받은 경우에는 기존의 제한된 분류 규칙으로 업무를 선택하고 프롬프트를 `requirements`로 옮긴다. 구조화 요구사항과 프롬프트를 함께 받은 경우 추가 지시는 `instructions`로 보존한다. 기존 `instructions`가 있으면 프롬프트와 해당 지시를 순서대로 합쳐 어느 쪽도 잃지 않는다. Worker에는 정규화한 요청을 전달한다. 원래 프롬프트는 사용자 입출력 이력으로 남으며 실행 입력을 우회하는 별도 지시로 전달하지 않는다.

입력 객체의 키를 정렬한 canonical JSON에 SHA-256을 적용한다. 배열 순서는 의미가 있을 수 있으므로 유지한다. 요청·입력 스키마·업무·규칙·workflow·작업 유형·한도를 실행 레코드에 고정하고, 실행 코드와 의존성 잠금 파일의 지문도 함께 보존한다. `GET /runs/:id`는 정규화된 `request`, `request_digest`, `definition_digest`를 반환한다.

자연어 분류 자체의 의미 정확성은 아직 보장하지 않는다. 복합 업무 분해와 모델 기반 분류기는 후속 범위다. 자동화에서 분류의 모호함을 제거하려면 명시적인 구조화 요청을 사용한다. 일반 사용자에게 이 내부 계약 작성을 필수로 요구하지 않는다.

## 실제로 집행하는 workflow

현재 지원하는 산출물 흐름은 `produce 또는 plan → verify → review → render`다. 검증·검토에서 `revise`가 나오면 `repair → verify → review`로 연결한다. 다음은 현재 정의의 검토 노드다.

```json
{
  "review": {
    "task": "review",
    "on": {
      "done": "render",
      "revise": "repair",
      "blocked": "$blocked",
      "failed": "$failed"
    }
  }
}
```

노드 이름과 작업 유형은 별개다. `assess`라는 노드가 `review` 작업을 수행하도록 바꿔도 권한·응답 검사는 작업 유형을 기준으로 적용한다. 엔진 어댑터는 다음 노드에 관여하지 않는다.

서비스 시작 시 다음 조건을 검사한다.

- 시작 노드와 모든 전이 대상이 존재하고 모든 노드에 도달할 수 있다.
- 작업 유형과 실행 방식이 일치하며 검증·검토 작업은 산출물을 쓰지 않는다.
- 생성·수정 후 검증, 검증 후 독립 검토, 검토 후 최종 전달을 생략하지 않는다.
- `blocked/failed`를 완료로 바꾸지 않는다. `revise`는 예산이 있는 수정 노드로만 연결한다.
- 반복 경로에는 수정 예산이 있고, 별도의 전체 단계 한도가 있다.

실행 시 worker의 `status/result`를 검증한 뒤 정의된 전이만 적용한다. Worker가 `next` 같은 필드를 추가해도 실행 권한이 생기지 않고 응답 계약 위반으로 실패한다. 수정 진입은 최대 2회이며 한도를 넘으면 `repair_limit` 사유로 차단한다. 생성 workflow의 전체 단계 한도는 12회다.

각 수정은 새 산출물 버전을 만들며 기존 검증·검토 통과 근거를 승계하지 않는다. `render`는 현재 산출물 해시에 연결된 실행 검증과 독립 검토가 모두 통과했는지 다시 확인한다. 파일 반영 직후 crash가 발생하면 기존 intent와 실제 파일을 대조하고 복구 전이에 `publication_reconciled`를 남긴다.

`checks.run`과 `verification.report`도 각각 `verify`, `render`의 단일 노드 workflow로 수행한다. 실제 검사 실행과 근거 렌더링이므로 모델을 호출하지 않는다. 실패 보고서 생성의 완료가 검사 통과로 바뀌지 않는다.

이 구현은 제한된 내장 상태 기계다. 임의의 복합 산출물 DAG, 병렬 분기·합류, 동적 재계획, Git 통합까지 구현한 것은 아니다. 업무 추가는 현재 지원하는 작업·산출물·흐름의 범위 안에서 정의로 확장한다.

## 전이 기록과 모니터링

실행 DB의 `workflow_steps`는 run·epoch·순서, 노드와 작업 유형, 수행 상태, 시작·종료 시각, 결과, 다음 노드와 종료 사유를 저장한다. `status=completed`는 해당 단계 호출을 마쳤다는 의미이고, 품질 판정은 `outcome.status`와 다음 전이로 구분한다. 검토의 `revise`도 정상적으로 끝난 단계 결과다.

서비스 재시작 시 끝나지 않은 단계는 `interrupted`로 남긴다. 관찰하지 못한 성공이나 원래 종료 시각을 만들지 않는다. 재개 epoch별 전이와 subprocess 시도를 분리해서 조회할 수 있다. CLI의 `status <run-id>`와 실행 API에서 이 기록을 제공하며 GUI에 별도 오케스트레이션 로직을 추가하지 않는다.

같은 고정 정의와 같은 유효 결과의 순서는 같은 전이를 만든다. 입력 해시가 같다는 이유로 모델 응답까지 같다고 가정하거나 과거 품질 판정을 무조건 재사용하지 않는다.

## E2E 검증

Node **22.17.0**에서 하네스 자신의 `checks.run → verification.report` 업무로 실행했다. **E2E 65개(서비스·CLI·설치 55개, 브라우저 GUI 10개)가 통과**했고 실패·skip·flaky는 0개다.

| 시나리오 | 확인 결과 |
|---|---|
| 프롬프트 없는 `task/input` 요청 | 실제 subprocess·검증·검토·전달과 단계 기록까지 완료 |
| 7개 업무의 잘못된 입력, 미등록 필드 | run 및 subprocess 생성 전에 거부 |
| 프롬프트와 구조화된 지시를 함께 제출 | 두 지시를 정규화 입력과 worker 프롬프트에 모두 보존, 빈 지시는 거부 |
| 키 순서가 다른 동일 입력과 같은 판정 | 같은 입력 해시와 전이 순서 |
| 한 번 수정 및 계속되는 수정 요구 | 재검증·재검토 수행, 2회 이후 차단 사유 기록 |
| Worker의 다음 노드 지정 시도 | 응답 계약 위반, 필수 검사 생략·산출물 전달 불가 |
| 노드 이름 변경 | 실제 worker 호출과 상태 전이가 변경된 정의를 따름 |
| 검증 생략·실패를 성공으로 연결·무제한 수정·없는 노드 | 서비스 시작 실패, 요청을 수락하지 않음 |
| 파일 반영 직후 crash | 파일·intent 대조 후 복구 완료와 전이 사유 보존 |
| macOS 패키지 | 번들 Node/의존성/스키마로 서비스 시작, 잘못된 입력 거부, 검사 미실행과 보고서 전이 기록 |

실행 근거는 `output/self-verification/2026-09-16T16-29-17.498Z/result.json`과 같은 디렉터리의 `verification.md`, 패키지 검증은 `output/package-validation.json`에 있다. `output/self-verification/latest.json`은 가장 최근의 자체 검증을 가리킨다.

실제 프로세스·API·SQLite·파일·브라우저를 사용했으며, 모델 결과는 fixture 또는 CLI 프로토콜 대역이다. 실제 모델의 내용 품질은 이 테스트로 검증하지 않았다. 스키마와 오케스트레이션은 계약·순서·필수 근거를 강제한다. 사업 판단·사실 정확성·디자인 품질은 업무별 검사·독립 검토·실제 사례 평가로 계속 확인해야 한다.

0.3.0 macOS 앱과 ZIP을 다시 빌드했다. 현재 사용자 설정·훅·LaunchAgent 설치, 실제 모델 호출, 외부 배포는 수행하지 않았다.
